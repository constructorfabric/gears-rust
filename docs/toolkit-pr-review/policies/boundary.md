# Boundary evidence v3: local Git adaptation

## Discovery

Apply every assigned criterion to every changed file and read the whole file. Report all independent supported defects; neither a minimum number of findings nor an empty result is a goal. Compare head/base to distinguish introduced defects, incomplete newly promised behavior, preexisting limitations and intentional changes. Read-only inspection of unchanged consumers is part of the review; the diff restricts report anchors, not evidence gathering. When changed behavior introduces or relies on implicit context, scoped state, inherited configuration or a cross-boundary guarantee, trace installation -> consumer -> execution/lifetime boundary -> actual use. Inspect relevant task/thread handoffs, queues, callbacks, lazy streams and cancellation/cleanup boundaries. A span, copied security context or suggestive type name does not prove that independent state is transferred. Follow real production consumers and their dispatch abstractions, not just references to the new helper. Keep a working list of concrete suspected broken guarantees and resolve it before declaring the pass complete. This is a draft source pass. A separate closure pass will inspect its claims and unresolved consumer paths before any successful checkpoint. Keep concrete incomplete paths in notes, including the next unresolved dispatch edge; do not silently replace a runtime hypothesis with a documentation suggestion. Emit internal boundary_obligations in the draft pass: an array of {id,hypothesis,next_edge}, with IDs <module>:chain:<index>. Include every concrete cross-boundary suspicion, including one not emitted as a finding because its consumer remains untraced; use [] only when none applies.

## Closure evidence

For a credible cross-file hypothesis, use review.py source --search on pinned head/base to locate consumers and implementations, including unchanged code, then source --path for relevant units or full files. Start from the changed producer/consumer and narrow broad boundary searches by the related subsystem; inspect continuation or narrow a query when the first page contains unrelated hits or mostly declarations/mocks. References are lexical hints, not resolved call edges. Empty search results and tool failures do not establish absence: fall back to the pinned Git source reader. Before dismissing an identified boundary risk as "no concrete caller", perform a bounded follow-up search and inspect at least the relevant production handoff and consumer, or explicitly record the searches, unread dependencies and unresolved conclusion in notes. If required source evidence cannot be read, use partial rather than claiming a completed check. A fully investigated hypothesis may be rejected; do not invent a finding to complete a checklist. Record the path checked and the normal/rejecting control in notes. For each emitted claim give concrete preconditions, the actual call path, violated contract and observable consequence. MEDIUM also requires nonempty impact describing a meaningful realistic failure, not simply a possible mutation, lack of a test, maintenance preference or absence of HIGH evidence. For coverage, identify a plausible incorrect implementation of the changed behavior and check whether existing unit/integration/generated tests would detect it under the relevant features; an additional assertion alone is not a blocker. A significant uncovered integration contract may justify MEDIUM without claiming a present runtime bug. For security distinguish an untrusted value from an exploitable sink: establish the sensitive information, actual trust boundary or meaningful resource/operational damage. Correlation identifiers are not automatically credentials or tenant identity. Respect documented intentional breaking changes; an optional migration diagnostic alone does not justify MEDIUM. Keep recommendations within the proved, PR-introduced claim. Uncertainty belongs in notes or precisely bounded claims, not invented consequences. When search hits are unrelated, narrow pinned Git search by subsystem, then read the actual caller, concrete implementation and send operation. Follow trait/interface dispatch, factories and dependency wiring to the implementation used by the production caller. A call that passes a security/context object or instruments a span does not transfer independent task-local state. Certainty is distinct from severity: a deterministic observability-only failure is not HIGH. HIGH/CRITICAL requires a separately evidenced substantial functional/operational failure, sensitive disclosure, security boundary breach or data loss, not just lost correlation, less convenient incident triage or a violated diagnostic promise. Do not lower a real authorization/tenant boundary defect because its state happens to be propagated as context.

Use policies/pass-contract.md for the local transport envelope and v2 audit fields. No RAG server is configured or required. Inspect pinned Git objects rather than current working-tree files.
