## 1. Read this first — why the previous pass stopped

Four remediation waves ran on this set: **74 → 25 → 63 → 48 findings**. The count is not
converging, and in the last wave the remediation *introduced* several of the defects the
verification then found — including one authorization bypass and two schema declarations that
cannot be created in any database. The previous pass stopped deliberately rather than run a fifth
sweep.

**Counts, precisely.** Two reviewers emitted **48 finding ids** — `Rc2-001`…`Rc2-036` from the
consistency pass and `F2-SEM-001`…`F2-SEM-012` from the artifact checklist's SEM category. Five
are cross-reviewer duplicates (marked in §7), so there are **43 distinct defects**, of which
**11 are CRITICAL**. The consistency reviewer's own header says "9 CRITICAL · 20 MAJOR · 5 MINOR =
34" against the 36 ids it emitted; its arithmetic is off by two, which is itself an instance of the
defect class this set keeps producing.

**The single most important thing to know: a green gate here means almost nothing.**
`cfs validate` checks artifact *form*, not semantic correctness. Do not treat a passing
artifact validation as evidence that a fix landed; review the affected sections directly.

**The recurring failure mode**, in order of how often it has bitten:

1. **A `DECISIONS.md` entry names propagation addresses and the named sections are never edited.** Six occurrences in wave 3, five more in wave 4. Always open every address and read it.
2. **A headline count is fixed and a prose enumeration of the same thing is not.** Ports, predicates, matrix rows, refusal classes, ADRs, tables.
3. **A `MUST` is written for a column, enum value or index that does not exist** in `01-foundation.md §3.7`, which is the canonical schema.
4. **A fix is applied to the normative section and not to the slice's own §1.1/§1.2 vision text**, so the superseded mechanism survives where a reader starts.

## 5. Tier 0 — do this one first, alone

### Rc2-009 · CRITICAL · authorization bypass · **verified**

`design/01-foundation.md` §3.6 step 1 is an idempotency probe that returns a committed order's
stored outcome. The authorization pre-guard is **step 5**, inside the transaction. So as
specified, any caller supplying a matching `(operation, idempotency_key)` and request fingerprint
receives the stored outcome **before any authorization check**.

The same file's §4.1 still states the normative order as *"authorization, then idempotency
resolution, then state-table admissibility, then the version check, then slice guards"*, and
§3.6's own Description says *"Authorization precedes everything so an unauthorized caller learns
nothing about the order's state."* The algorithm contradicts both, and the algorithm is the
permissive one.

**Introduced by** D-65 in wave 3, while fixing PRD §12 AC-4 (a replay must not re-run the gate).

**Fix — pick one and state it in `§4.1`, `§2.1` and §3.6's Description:**
- **(a) preferred** — evaluate authorization *before* the probe. Requires the authorization inputs to be resolvable outside the transaction, which they are (`08 §2.1`'s shared evaluator is invoked from read paths with no transaction).
- **(b)** — keep probe-first but restrict its return to a caller whose principal matches the stored record's actor, and say so normatively.

Either way, correct the "precedes everything" sentence and re-order or annotate the `§4.1`
sentence so the normative statement and the algorithm agree.

**Verify**: the step order in §3.6 matches §4.1's sentence verbatim; a test asserting an
unauthorized caller with a valid key and matching fingerprint is refused, not served.

### Rc2-001 · `01-foundation.md` · a draft cannot carry version 1 · **verified**
§3.7 says *"Creation appends version 1 — an empty commercial document — so `current_version` is
never null"* and declares `current_version` **NOT NULL, `1` from creation**. But §4.3 **row 1** is
`(state-only, event —)`, and §3.6 **step 18** appends a version *only* `IF the row's versioning
behaviour is versioning`. `04 §3.3` also says *"only four transition rows append a version, and
all four are submit or amendment"*, and D-82 closes `orders_order_version.reason` to
`{submit, amendment}` — so no reason value exists for a creation version.
**Fix**: choose one shape. Either make row 1 a versioning row and widen the reason vocabulary
(touching D-82, `01 §3.7`, `04 §3.3`, `04 §4.5`), or keep row 1 state-only, make `current_version`
nullable through the draft phase, and re-derive PRD §12 AC-1 compliance another way — stating
explicitly what `expected_version` a draft mutation (row 2) and administrative edit (row 3)
present, since the version check is mandatory on every transition.
**Escalate if** you cannot satisfy AC-1 without a version row; that is a PRD conversation.
**Verify**: the set of version-appending rows in §4.3 equals the count in `04 §3.3` and D-82, and
every such row's reason is in the enum.

### Rc2-003 · `03-gate-and-pin.md` §3.7 · order market stored on the wrong table · **reported**

**Fix**: rewrite to name `orders_order_version.market_currency` / `market_region`, re-derived and
re-stored per amendment.

### Rc2-031 · `01-foundation.md` §3.7 · the in-flight index cannot be created · **verified**
Declared on `orders_order_line`: *"a **partial unique index** on `(payer_tenant_id,
overlap_scope_key)` `WHERE state IN ('submitted','pending_approval','approved','in_fulfillment',
'on_hold')`"*. Confirmed: `payer_tenant_id` and `state` are both columns of **`orders_order`**;

and the two-concurrent-identical-submits hole D-26 closed is open again.
**Fix**: either denormalise `payer_tenant_id` and `state` onto `orders_order_line`, or relabel it
a sixth engine-enforced invariant with a named test and correct D-26 and `03 §4.2` predicate 9.
**Escalate**: concurrency correctness.

### F2-SEM-001 · `06-workflow-seam.md` §4.2 · the two-step seam has no upstream ask · **verified**
`06 §4.2` places a `MUST` on the sibling gear: on consuming `OrderAmended` it must obtain the new

specified exit from `submitted` and dwells until its TTL expires it.
**Fix**: add a §2.6 to `UPSTREAM_REQS.md` with `orders-workflow` in §1.2, stating the
`OrderAmended` obligation; extend Q-12 to name the Workflow PRD as needing amendment; cite the ask
from `06 §4.2`, `06 §4.6` and `04 §4.3`.

### F2-SEM-002 · `08-read-and-authz.md` §4.3 · Seller Operator may record the buyer's consent · **reported, escalate**
The matrix grants Seller Operator **record acceptance** *"on recorded customer instruction"*, and
`05 §4.2` restates it. PRD §6.6 grants Seller Operator only hold, resume, cancel-with-reason and

Consequence: the selling party — the one with the commercial incentive for fulfilment to proceed —
can record the buyer's consent, gated on an unspecified artifact. That is the control PRD §6.1
introduced the acceptance instant to provide.
**Fix**: either remove the cell (and the matching sentences in `05 §4.2` and `08 §4.3`), or keep it
and route a new open question with Product as owner **plus** specify the instruction artifact.
Apply the same §6.6 test to the Seller Operator administrative-edit and the three Preview grants.
**Escalate**: authorization scope.
