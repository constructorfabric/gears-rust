# S2-07 transactional in-flight overlap claims

Status: **implemented, independently gap-fix reviewed and locally verified**. The scope is step 17 of [Attempt Transition](../features/01-foundation.md#contract-01-3-6) over the [claim table](../DESIGN.md#contract-01-table-orders_inflight_overlap_claim). Of the public business operations only draft authoring and the draft reads are exposed (S2-09, early S6-01/S6-04, S2-12); submit and amendment, the rows that take claims, stay unavailable. The engine (S2-04) is the only intended production caller.

## Delivered

| Area | Implementation |
|---|---|
| Pure rules | [domain/overlap.rs](../../orders-lifecycle/src/domain/overlap.rs). `ClaimTuple` is the full `(payer, resource tenant, overlap key)` identity. Its derived order is the normative total order: payer UUID bytes, then resource UUID bytes, then key UTF-8 bytes, independent of database collation. `OverlapScopeKey` stores the owner's key verbatim and refuses only empty or NUL text. `ProposedClaims` deduplicates line keys. `plan` partitions held and proposed full tuples into retained, missing and superseded, and refuses a repeated live tuple |
| Engine contribution adapter | `ClaimDirective::for_transition(trigger, effective_target, keys)`. A terminal target (§4.3) gives `ReleaseAll` (17.1). Submit and amendment with keys give `Replace` (17.3–17.6). Other rows give `Retain` (17.2). Keys on any other row, or missing keys on submit/amendment, are contract errors that abort the transaction |
| Transactional repository | [repo/claims.rs](../../orders-lifecycle/src/infra/storage/repo/claims.rs) `LockedOrder::maintain_claims`, under the aggregate lock in the caller's transaction. It validates the complete proposed arrangement against its own PDP scope and requires a candidate version above the current one. It locks this order's live claims and offers each missing tuple in order with `ON CONFLICT … WHERE released_at IS NULL DO NOTHING`. `claimed_at` is `clock_timestamp()` read inside the transaction; no caller can supply it. Before its first claim statement, acquisition and terminal release check `current_setting('transaction_isolation')` and abort unless it is READ COMMITTED, so a snapshot transaction can never turn a collision into a serialization failure. `release_claims` is the only claim mutation; there is no generic claim replace, so `released_at` is always database time, exact-ID and count-checked. On a shortfall it releases exactly the IDs the database returned (count-checked, skipped when empty) and keeps every claim held on entry. It names a blocked tuple's holder only through the caller's order-read scope (D-179). After complete acquisition it releases superseded tuples. `transition_tx_config()` pins READ COMMITTED |
| Refusal | `ClaimOutcome::Conflict(OverlapConflict)`: `OverlapConflict::REASON` is `order-in-flight-for-key`, a failed slice guard. The engine audits it through S2-06 `append_resolved_refusal` and settles it through S2-05 `Owned::settle(Settlement::Refused)` in the same transaction, then commits. Every `ClaimStoreError` aborts the transaction as an infrastructure outcome |

## Boundaries

- **S2-04** calls `ClaimDirective::for_transition` after step 14 and `maintain_claims` at step 17, before the version append. It opens transitions with `transition_tx_config()` (the repository refuses any other isolation level as an integrity abort), maps `Conflict` to the audited and settled refusal, and maps every error to rollback.
- **Stage 3 (S3 assessment/diagnostics)** persists the reached assessment, with advisory predicate 9 replaced by `OverlapConflict::predicate_nine()`. Gate-outcome rows, run metadata and the mapping version belong to the assessment owner. Until then the refusal settles without diagnostic rows, and no gate-outcome row is invented.
- **Stage 5 (S5-06a/b)** deduplicates Orders claims against receiver reservations using the exact order/version/line/attempt linkage. D-182 `force-fail-unreconciled` releases Orders claims through the ordinary terminal rule. Uncertain Subscriptions receiver capacity is a different store that this package never touches.
- **Cardinality.** Orders claims enforce only the fixed one-in-flight-order rule (PRD §6.1(g)). They do not enforce Subscriptions' concurrent-subscription cardinality (§6.1(f), predicate 7, `upreq-overlap-activation-atomicity`).
- **Deadlock scope.** The total order prevents opposite-order waits among claim tuples. As DESIGN states, it is not a blanket deadlock-freedom claim for transactions that already hold other locks.
