# S2-05 idempotency and durable execution ownership

Status: **implemented, independently gap-fix reviewed and locally verified** (gap review: `artifacts/orders-lifecycle-s2-20261006/S2-05-gap-review.md`). Scope is the registry rules, the authoritative transactional gate, the advisory probe, replay disclosure through the shared PEP, and D-188/D-198 durable execution ownership. Of the public business operations only draft authoring and the draft reads are exposed (S2-09, early S6-01/S6-04, S2-12); submit, amendments and fulfillment stay unavailable. The engine (S2-04) is the only intended caller.

## Delivered

| Area | Implementation |
|---|---|
| Registry rules | [domain/idempotency.rs](../../orders-lifecycle/src/domain/idempotency.rs): `(operation, principal_scope, key)` identity; stable `subject_tenant/subject` principal (anonymous/nil refused); request fingerprint over exactly the §4.2 inputs; D-173 retention class (exact nine workflow-class triggers → 30 days, all others 24 hours); positive finite lease; checked fence increment; gate classification (retention expiry → fingerprint → settlement → owner → lease); closed `formatVersion = 1` response snapshot whose headers are limited to the closed semantic set `Content-Type`/`ETag`/`Location` (no credential, proof or transport header; case duplicates and control characters refused) |
| Fingerprint bytes | Fingerprint `operation` must be a registered state-changing catalog operation (or the D-201 internal `replace_fulfillment_grant`). Adopts the S1-06 request profile v1 byte-for-byte (see [CONFORMANCE](CONFORMANCE.md#proposed-requestcursor-byte-profiles)); SHA-256 through the FIPS-validated `aws-lc-rs` provider (DE0708), stored as `rf1:<hex>`. Both frozen vectors match their independent Python preimages and digests |
| Authoritative gate | [repo/idempotency.rs](../../orders-lifecycle/src/infra/storage/repo/idempotency.rs) `resolve`: create takes no aggregate lock; every other operation presents its `LockedOrder` (aggregate before registry before linked attempt/control). Locked read, then fresh `clock_timestamp()`; conflict-safe insert distinguishes own insert from a winner (re-read, bounded rounds); narrow expiry replacement of exactly the locked generation; ordinary reclaim replaces only the lease; durable reclaim rotates owner token and fence on marker and linked execution together; a reclaimed durable marker that was never linked starts its execution under the rotated fence instead of stranding the key. `Owned` borrows the claiming transaction and settles there |
| Advisory probe | `probe`: unlocked, after authorization and before input resolution; replays only a matching, settled, unexpired record bound to the same target; a matching unresolved D-188/D-198 execution returns its frozen inputs (resume before fresh assessment); everything else misses |
| Replay disclosure | [execution.rs](../../orders-lifecycle/src/infra/execution.rs) `disclose_replay`: wires S2-03's `Pep::recheck_replay_disclosure`; create replays require fresh `order × read` on the created order; lost access is non-disclosing and never a second create |
| Durable ownership | `begin_commercial_attempt` (checked high-water candidate allocation, candidate stamped into line requests, attempt + marker link), `begin_fulfillment_control` (one pending control, pointer set), `verify_owner`, `record_receipt`, `record_control_progress` (immutable first results; nonterminal status only advances, typed `StatusRegression`), `finish_execution` (terminal execution + conditional pointer clear + settlement in one transaction) |
| Configuration | `OrdersConfig::idempotency_lease` maps the existing validated setting to the domain lease |

## Boundaries

- The engine (S2-04) composes these primitives with state/version/guards, audit (S2-06) and outbox (S2-08); refusal/mismatch/still-processing audit rows are its responsibility. Stale-authorization conflicts (S2-03 `AuthorizedLock::Stale`) end before the gate and never touch the registry.
- Recovery continuation inside the idempotency maintenance worker (bounded batches, abandonment policy, backlog metrics) is S2-11; Pricing commands/receipt selection are S3; receiver barrier evidence and Workflow coordination are S5.
- Cross-principal create duplication and post-retention re-execution remain the disclosed Foundation §4.2 limitations.
- Resolved by D-203 (2026-10-06): the D-201 internal `replace-fulfillment-grant` is in the workflow **retention** class (≥30 days) without joining the §4.1 workflow-trigger guard-order class. `RegistryOperation::retention` returns `Workflow` for it; covered by `retention_class_is_exactly_the_workflow_trigger_class` and the PostgreSQL `claims_stamp_db_time_and_operation_windows_and_never_extend_them` (720-hour window stamped for a `replace-fulfillment-grant` claim).
