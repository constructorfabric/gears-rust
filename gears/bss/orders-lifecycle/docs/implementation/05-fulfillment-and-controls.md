# Stage 5 — Fulfillment, lifecycle controls and bounded lifetime

This is an implementation plan, not a claim of delivered runtime. It covers all of [Workflow seam](../features/06-workflow-seam.md) and [Hold and expiry](../features/07-hold-and-expiry.md), including their detailed algorithms, acceptance criteria and D-188/D-198 amendments. Build the missing Workflow and Subscriptions capabilities as packages below; a mock-only Orders implementation does not complete this stage.

## Entry conditions and ownership

Prerequisites are deliverables, not assumed stage-number completion: Foundation supplies the sole transition writer, PolicyEnforcer-scoped SDK/REST boundary, registered state/guard/reason tables, immutable audit, producer outbox, execution-generation idempotency, bounded maintenance runtime and database harness; Capture/Gate/Versioning supply exact committed schema-2 receipt/query/binding snapshots, sparse versions, stable line identities and overlap claims; Preconditions supplies actor/version-bound customer acceptance and payment authorization outcomes. Shared read delivery must already expose authorized exact-version roster/market/payer/receipt data. Approval/Contracts/Payments production providers from the preceding integration packages must be connected before production begin-fulfillment.

Implement proposed paths only after checking the repository's actual crate layout. In this plan `O` means proposed `gears/bss/orders-lifecycle/{orders-lifecycle-sdk,orders-lifecycle}`, `W` means proposed `gears/bss/orders-workflow/{orders-workflow-sdk,orders-workflow}`, and `S` means proposed `gears/bss/subscriptions/{subscriptions-sdk,subscriptions}`. These implementation crates were absent in the reviewed tree. Reuse any concurrently delivered skeleton rather than create duplicates. Read [ToolKit layout/SDK](../../../../../docs/toolkit_unified_system/02_gear_layout_and_sdk_pattern.md), [database](../../../../../docs/toolkit_unified_system/11_database_patterns.md), [authorization](../../../../../docs/toolkit_unified_system/06_authn_authz_secure_orm.md) and [stateful lifecycle](../../../../../docs/toolkit_unified_system/08_lifecycle_stateful_tasks.md) before coding. Changes to dependencies also require [DEPENDENCIES](../../../../../guidelines/DEPENDENCIES.md).

A package completes only with its provider implementation, applicable migrations/grants, executable acceptance evidence and updated contract traceability. Commands run through the repository's supported Cargo/test tasks discovered from existing crate manifests; do not invent executable crate names. PostgreSQL tests are mandatory for locking, uniqueness, isolation and worker races; SQLite or mocks cannot establish those guarantees. Public state changes/audit/outbox remain one engine transaction. Network calls never run under an Orders SQL lock.

Patch the peer normative prose/fixtures to that selected behavior before implementation. If a real product now requires dependency edges, stop only that extension for a separate owner contract; do not resurrect an undocumented graph inside Workflow.
3. **Draft rebuild/grant gap:** D-198 immutable grant rosters contain create keys, while Workflow must rebuild auto-voided drafts. An intent cannot know a future OSS-confirmation timestamp. **Recommendation:** receiver records the actual service-effective instant from its authoritative applied outcome; request carries the admitted activation intent instant and quoted date separately. Confirm its compatibility with frozen BillingTerms/hold activation identity before implementation. If it would change the selected accepted terms, refuse/resubmit rather than silently choose a new billing anchor.

**Acceptance:** approved contract fixtures cover sparse version 4→7; original draft versus rebuilt wave keys; same timestamp but changed audit generation invalidates forced approval; old graph failure decoding; precise actual-start/quoted-start separation. Items 3, 4 and 6 require normative contract updates in this package, not merely implementation comments. Product-owned TTL confirmation, cap policy qualification and peer deployment approval remain separately tracked, not prerequisites to seeded local implementations.

**Local delivery:** [RECEIVER_CONTRACTS](RECEIVER_CONTRACTS.md) records D-201 amendments, operation/alias matrix and updated fixtures. Runtime delivery and peer deployment conformance remain in their assigned packages.
