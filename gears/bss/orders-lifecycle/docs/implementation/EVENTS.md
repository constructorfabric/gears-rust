Of the public business operations only draft authoring and the draft reads are exposed (S2-09, early S6-01/S6-04, S2-12), and no delivered operation emits yet: create and draft mutation are event-less (§4.4); the eventful rows (submit, amendments, holds, cancel, fulfillment) stay unavailable. ## Boundaries and open items

- **S2-04** owns calling `transaction`/`enqueue` on each event-producing row, building the summary from the committed post-state and the specific fields from the row's contribution. The rows are 4–6, 8–10, 13–29 per §4.4. S2-08 enforces *at most* one message per attempt and *no commit after a failed enqueue*. *At least one* message on an eventful row needs the S2-04 row table, so it remains S2-04 acceptance.
- **Partition count.** No broker API reports it, so §3.7's "startup MUST fail" cannot be enforced. A real-broker probe shows a mismatch silently drops events: 12 committed gave 8 stored, 2 dead-lettered and 2 answered `Duplicate` for a different event. The matched control stores all 12. The mechanism is described as an upstream defect in [UPSTREAM §2.7](../UPSTREAM_REQS.md#27-event-broker). **DESIGN §3.7 is amended by D-205:** the count is the required `events.broker_partitions` declaration, equality with the broker is a deployment gate under `upreq-event-broker-runtime` (S6-05), and UPSTREAM_REQS §2.7 requests a broker-level partition-count capability so startup can fail on a mismatch later. The silent loss itself is a **deferred escalation** (COORDINATION "Deferred escalations"; UPSTREAM_REQS §2.7): recorded, not yet raised with Event Broker.
- **Schema expressiveness.** The registry compatibility checker admits no `if/then/else`. The JSON schema therefore admits ordinary or forced evidence, while the reason-to-variant and `forcedReason` coupling (D-182) is enforced by Orders before enqueue.
- **Grants.** Deployment must grant the producer `produce` for the Orders family under the root tenant only. The bundled rules provider now expresses the broker's property-less `event_type` check as an exact unconditional grant and the tenant-scope check as a root-tenant-constrained rule; the [E2E fragment](../../config/e2e-orders-lifecycle.yaml) carries both, pinned to `events.producer_*` by `gear::tests::e2e_fragment_grants_event_broker_produce_to_exactly_the_orders_producer`, and the plugin test `event_broker_produce` drives the real ingest check with and without the grant. Production provisioning and root-source confirmation stay under `upreq-pdp-policy-integration` and `upreq-event-broker-root-tenancy`.
- **S6-05/S6-06:** operator dead-letter republication, consumer conformance, delivery monitoring and deployed revisions. No Orders re-drive path exists.
- Consumer-facing Rust event types are not exported from the SDK; the registered GTS schemas are the published contract.
