# License Manager PRD: acceptance test plan

This plan holds the per-requirement acceptance checks for the [License Manager PRD](PRD.md). PRD §9 keeps the business-level criteria.

- Each line checks one requirement and cites its ID. Every FR and NFR of the PRD has at least one line.
- The PRD is normative. Where a line and the PRD differ, the PRD applies and the line is corrected.
- Worked scenarios with data belong in the feature test plans (planned).
- Values such as 24 hours, 72 hours and 15 minutes are the PRD's proposed, configurable defaults.

## General

- [ ] Goals (PRD §1.3): each goal is measured as stated there. The bypass measure is read from the reconciliation report, excluding Phase 1 seat binds by the Tenant Administrator. Audit completeness compares License Manager's accepted and rejected attempts with the entries in the audit target.

## Phase 1

- [ ] Phase 1, `cpt-cf-license-manager-fr-pack-issue`: a pack is issued only to an active tenant, with a reason and an idempotency key; a replay returns the first result, and a reused key with other content is rejected. An issue to a tenant that has a live lineage, including a delegated child pack or a suspended pack, is rejected. An issue into a tenant that holds a foreign `source=licensing` Quota on one of the pack's metrics is rejected with a typed reason and changes nothing. An active Quota from another `source` on one of the pack's metrics does not block the issue; it is reported in materialization health and never adopted. Until OQ-45 closes, an issue to a self-managed tenant is rejected with a typed reason. An issue after a completed revoke, inside the revoked lineage's old window, is accepted. An issue while a step of an earlier revoke for the tenant is outstanding, also a step escalated as stuck, is rejected with a typed reason. After a failed first issue, version 1 reads "not applied" and no pack is in force; a new issue is rejected until a revoke ends it, and accepted after.
- [ ] Phase 1, `cpt-cf-license-manager-fr-reference-validation`: an unregistered, unavailable or incompatible reference rejects the whole request.
- [ ] Phase 1, `cpt-cf-license-manager-fr-mapping-capacity-rule`: every version records the mapping id, version and checksum; a missing or ambiguous mapping rejects the request.
- [ ] Phase 1, `cpt-cf-license-manager-fr-one-capacity-rule`: a request that would give a tenant two capacity Entitlements for one metric and period with overlapping windows is rejected, also when two requests for one tenant arrive at once; a new pack whose window starts where an Expired one ended is accepted.
- [ ] Phase 1, `cpt-cf-license-manager-fr-pinned-contracts`: a live pack keeps working after its app is uninstalled or re-seeded, and the affected pack shows in materialization health; a new issue or replace against the inactive contract or mapping is rejected.
- [ ] Phase 1, `cpt-cf-license-manager-fr-versioning-status`: Scheduled, Effective and Expired follow dates with no timer; only a version with nothing of its lineage in force can start in the future. A request to change a Superseded or terminated version, or to renew an Expired lineage, is rejected with a typed reason. From Phase 2a, a replace of a suspended pack leaves the lineage suspended. Every new version, also a replacement, reads "not applied" until its change is applied, and is never the lineage head. Its base becomes Superseded only when it is applied. In License Manager's records a failed or preempted replacement reads as such, never comes into force, and the base stays authoritative. A license-enforcement replace step that applied stays in force, the partial state is reported, and the next replace or revoke targets that Pack. A not-applied version leaves that state only in the listed ways; any other request, such as a replace of a not-applied version 1, leaves it not applied.
- [ ] Phase 1, `cpt-cf-license-manager-fr-expiry-cutoff` (OQ-2 for quota-enforcement): at `effective_until` both gears refuse new use under the pack with no License Manager action, and no Grant has a grace window.
- [ ] Phase 1, `cpt-cf-license-manager-fr-pack-replace`: a replace takes effect at once; a stale base, a cap below the protected minimum, and removal of an Entitlement still in use are rejected naming the shortfall; a later start for an Effective head is rejected; a replace that adds an Entitlement overlapping foreign state is rejected. A replace against a lineage whose version 1 is "not applied", with its first issue running or failed, is rejected with a typed reason; a running first issue continues unchanged.
- [ ] Phase 1, `cpt-cf-license-manager-fr-pack-replace`: a replace is accepted while a change on the lineage has a gear call in flight whose reply is then lost. The replace preempts that change. Once the replace is applied, no effect of the preempted change remains in either gear, also when the late call lands after the preempt. A replace rejected during a running change leaves that change untouched, and it reaches its own end state.
- [ ] Phase 1, `cpt-cf-license-manager-fr-pack-revoke`: once a revoke is accepted, reads show no pack in force even while a gear step retries; no applied revoke step is undone. The revoke deactivates the tenant Quota and, from Phase 2b, every user Quota of the pack; from Phase 2c, a parent revoke also deactivates the child Quotas. A revoke accepted during a partial replace, also one resumed after a restart, leaves no effect of the preempted replace once the revoke completes. A replace sent at the same time as a revoke on one lineage never leaves the lineage in force. From Phase 2a, the same holds for renew and reinstate. A revoke step rejected on a version conflict is retried with the current version, and the revoke never ends as failed. A revoke step that the gear reports as already done counts as done. A revoke step that the gears keep rejecting is retried, the lineage stays terminated, and the step follows `cpt-cf-license-manager-fr-stuck-steps`. A revoke sent while a delegate or replace on the lineage retries a failed gear step is accepted without waiting for that change, preempts it, and its latency counts from its request.
- [ ] Phase 1, `cpt-cf-license-manager-fr-pack-revoke`: while a gear read for a replace's validation hangs, a revoke on the same lineage is accepted at once. The replace ends as preempted, naming the revoke, and changes nothing. The revoke's latency counts from its request.
- [ ] Phase 1, `cpt-cf-license-manager-fr-pack-revoke`: a revoke preempts a replace whose gear call is in flight and whose reply is then lost. When the revoke completes, no effect of that replace remains in either gear, also when the late call lands after the preempt. An effect of the lineage injected into a gear after the revoke completed is found by reconciliation; the revoke resumes and removes it, and it is complete again only when no such effect is known.
- [ ] Phase 1, `cpt-cf-license-manager-fr-grant-materialization`: a pack version issued directly to a tenant has one license-enforcement Pack, one tenant-wide Grant per capability Entitlement and one unbound subject Grant per seat, each with the version's window and no grace window, and each traceable to pack id, version and Entitlement id; replaying the request creates no second Pack or Grant. Every root Grant and sub-grant is usable at once, with no acceptance requirement, and each seat Grant gives the holder bind permission. In Phase 1, each seat Grant is issued non-delegable.
- [ ] Phase 1, `cpt-cf-license-manager-fr-quota-materialization`: a breaking change never leaves two active licensing Quotas for one metric, and the usage restart is shown before confirmation.
- [ ] Phase 1, `cpt-cf-license-manager-fr-read-views`: the read view shows versions, history, derived status and materialization health with no pricing; in Phase 1 the seat, share and Child Delegation aggregate reads return zero for every Entitlement; a tenant with no effective pack is shown as having none; unavailable audit or health data is marked partial. A stuck step shows in materialization health with its tenant, lineage, step and rejections. The License Manager platform operator can read materialization health, drift and stuck steps across the deployment. No operator read returns a user id, even for a tenant with seat bindings. Each operator read writes an audit entry.
- [ ] Phase 1, `cpt-cf-license-manager-fr-reconciliation`: a direct change in license-enforcement, a foreign licensing Quota and a partial state each appear in materialization health within the interval, at the tenant and record volume the requirement states. So do a duplicate `source=licensing` Quota and an active Quota from another source on a licensed tenant and metric. A Phase 1 seat bind or unbind by the Tenant Administrator is shown, but is not drift and raises no operator signal. A drift-check read of Grants or Quotas that the gear refuses in a deleted tenant is reported as unverifiable, not as drift or a match. An effect of a preempted change injected into a gear after its replace was applied is reported as drift. One injected after its revoke completed is reported, and the revoke resumes and removes it.
- [ ] Phase 1, `cpt-cf-license-manager-fr-authorization`: each actor can call only the operations in its row, with tenant scope from the PDP and never from the payload. A Multi-Tenant Administrator acting for a parent tenant can delegate to, decrease and reclaim from its direct children, and cannot issue or replace a pack in a child. On a lineage bound to a BSS source key, an administrator can only revoke. Only the License Manager platform operator, within its scope (OQ-37), can confirm or release a stuck step and settle a partial change. Once the platform offers step-up, these actions require it. Each such action without a step id or correlation id, or without a reason, is rejected. Each accepted one writes an audit entry with its reason that Support / Auditor can read. A confirm by an actor without the operator role, or by the principal that sent the revoke, changes nothing. A repeated action, with the same action id or idempotency key, changes nothing further; a new confirm after a rejected one is checked again. Of a confirm and a release racing on one step, only the first is accepted.
- [ ] Phase 1, `cpt-cf-license-manager-fr-authorization`: a settle with a correlation id and a reason is accepted for a failed change whose effects partly stayed applied, and is audited with those effects. It ends the change inside License Manager and leaves those effects to reconciliation as drift; a BSS result stays `pending`, marked partial. A settle of any other change is rejected.
- [ ] Phase 1, `cpt-cf-license-manager-fr-visibility`: a machine caller reads only its own source keys. From Phase 2c, a parent reads per-child aggregates and the audit entries of its own Child Delegation and child-pack version changes, none with a user id, and no other audit entry from the child. After a child becomes self-managed, parent reads beyond its Child Delegation record fail closed until OQ-31 closes.
- [ ] Phase 1, `cpt-cf-license-manager-fr-idempotency-audit`: a replayed change applies once and a stale version is rejected; every accepted and rejected attempt has one audit entry with the listed fields, committed with the change, so no accepted change exists without its entry. A rejected attempt whose audit write is made to fail returns a retryable error, never an unaudited rejection. A platform operator action's entry records the operator, the reason and its object; a confirm's entry also records the read result, with no user id.
- [ ] Phase 1, `cpt-cf-license-manager-fr-stuck-steps`: a revoke, expiry or tenant-deletion step that the gears keep rejecting never ends as failed. It is escalated to the platform operator within 24 hours of its first rejection and is not retried automatically after that. It stays outstanding, and a new issue to the tenant stays rejected, until it succeeds or the operator's confirm is accepted. A confirm is accepted when a gear read of the step's Grant or Quota shows it done, or, with no gear read, when the tenant is gone for good (a `TenantNotFound` for a tenant already recorded as deleted). A confirm is rejected with its read result, and the step stays outstanding, when the read does not show the step done, or when the gear refuses the read, also in a tenant only recorded as `deleted`. A not-found for a tenant hidden by scope, or a `TenantNotFound` for a tenant not recorded as deleted, is also rejected. A release returns the step to retry and keeps it outstanding. Every confirm and release names the step, carries a reason and is audited; no stored or returned result holds a user id. From Phase 2a the same holds for a user-cascade step, and from Phase 2c for a child-deletion step.
- [ ] Phase 1, `cpt-cf-license-manager-fr-audit-store`: Support / Auditor reads audit entries in the audit target within PDP scope. From Phase 2c, a parent reads only the child entries that `cpt-cf-license-manager-fr-visibility` allows, once the audit target supports that filter (G20).
- [ ] Phase 1, `cpt-cf-license-manager-fr-data-lifecycle`: a tenant that account-management reports as `deleted` has its packs revoked, including a Scheduled-only or suspended pack, and its source keys closed within one reconciliation interval. A not-found, denied or failed status read revokes nothing, and a not-found raises an operator signal. A tenant-resolver `TenantNotFound` for a tenant not recorded as `deleted` starts nothing and raises an operator signal. For a tenant already recorded as `deleted`, for example after hard deletion, the cascade and stuck-step confirms proceed without the tenant record. After a revoke, an expiry or a tenant deletion, every seat assignment, contribution and residual of the lineage is closed, with its retention starting at the lineage end; after a replace, they carry over unchanged. A deletion step that a gear keeps rejecting follows `cpt-cf-license-manager-fr-stuck-steps` and never ends as failed.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-correlated-outcome`: a transient failure injected at each step, including a gear `ServiceUnavailable` answer, leaves every Grant and Quota at its prior or new value, is reported, and is retried until the change is applied; a restart in the middle of a change resumes it. A business rejection injected on a reduction step ends the change as failed, with no retry and no further forward step. Every Grant and Quota then holds its prior or new value, and any partial state is reported. A revoke during a running change ends that change as preempted, naming the revoke. A replace sent during a running change that fails validation leaves the change running; one that passes ends it as preempted, naming the replace. An authorization rejection of a revoke, deletion or cascade step is retried and escalated per `cpt-cf-license-manager-fr-stuck-steps`, and never ends the change as failed. A partial state is visible in the operation result and in materialization health.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-correlated-outcome`: for each operator condition that the requirement lists, a test that creates the condition shows it as a metric or health signal within the bound the requirement sets, and platform alerting can route it. A test that ends the condition clears the signal.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-correlated-outcome`: a tenant deletion cascade starts while a revoke and a first issue for the tenant are running. Each reaches its end state, and no pack of the tenant is in force. From Phase 2a, the same holds against the user cascade, and from Phase 2c against child deletion and the parent revoke cascade.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-concurrency-safety`: at no instant do parent use, Child Delegations, shares and seats exceed an Entitlement, counting accepted changes not yet applied, and nothing is counted twice across parent and child. A revoke sent during any running change or validation is accepted at once and preempts it. From Phase 2a this covers seats, from Phase 2b shares, and from Phase 2c delegations.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-concurrency-safety`: a replace whose validation read hangs, so that its validation cannot finish, changes nothing and ends with a retryable result. A later replace on the same lineage is then validated without waiting for it. A resend with the same idempotency key is processed again, not answered with a stored result.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-concurrency-safety`: a validation that cannot finish, and a validation preempted by a revoke, each leave the idempotency key and the BSS revision unused. A resend with that key, or of that revision, is processed again.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-concurrency-safety`: two issues to one tenant sent at once give exactly one accepted issue. An issue sent while a revoke for the tenant has a step not yet done is rejected with a typed reason. Of two replaces sent at once naming the same last applied version, exactly one comes into force. The other ends preempted, naming it, or is rejected, and leaves no effect.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-concurrency-safety`: an issue or a replace arrives after a conflicting change is accepted and before it is applied. It is rejected by the one-lineage rule, the one-capacity rule or the free-capacity check, as it would be after the apply. A replace on a lineage whose running change is not a first issue supersedes that change instead (`cpt-cf-license-manager-fr-pack-replace`). From Phase 2a, the same holds for an assign, a share change, an unassign, a renew, a suspend, a reinstate and a bulk change on the same Entitlement.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-concurrency-safety`: after an accepted change ends failed or preempted, a new change that needs the capacity it held is accepted. Only the effects that stayed applied still count.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-pack-latency`: with healthy gears that accept the steps, issue and replace of a pack with 50 Entitlements and 1,000 Grants and Quotas reach applied within p95 1 minute. Within p99 1 minute and never over 5 minutes of a revoke request, no license check or new debit succeeds under the pack. A Quota create still in flight when the revoke reads is removed within one reconciliation interval instead (G3). A Quota from another source on the same metric is outside the bound (OQ-5). From Phase 2b the bound covers user Quotas, and from Phase 2c the child Quotas of a parent revoke.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-reduction-safety`: usage that grows between the decision read and the write is caught by the second read or the named gear guard, and no reduction ends below the protected minimum. A revoke or deletion of a pack with usage above zero is not rejected for that usage, because a termination is not a reduction.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-recovery`: after a restore to an earlier point, every difference with the gears is reported before a new change other than a revoke is accepted. A License Manager restart loses no accepted change and no source fence.
- [ ] Phase 1, `cpt-cf-license-manager-nfr-dependency-outage`: with each dependency down in turn, every operation ends with the effect in its row. While the PDP cannot authorize callers, a new revoke is rejected, and a revoke accepted before the outage completes.

## Phase 1b

- [ ] Phase 1b, `cpt-cf-license-manager-fr-source-fencing`: a repeat, an older revision and a request after revoke have no effect; conflicting content under one revision is rejected; a caller reads only its own operations; until OQ-11 closes, a new source key for a tenant with a live lineage is rejected. A revoke from BSS that ends a failed first issue leaves the source key open, and a new revision under that key is accepted. An administrator's revoke of a not-applied version 1 closes the source key, and a later BSS revision under it has no effect. A tenant deletion closes every source key of the tenant, also one that a BSS revoke left open. An older revision replayed after records of the lineage are purged has no effect.
- [ ] Phase 1b, `cpt-cf-license-manager-fr-desired-grant-apply`: results follow the four defined values. An apply with an injected `CAP_BELOW_CONSUMED` before any step is applied ends `refused`. An apply preempted by a revoke ends `refused` as preempted, naming the revoke. Restricted and continuation are refused until Phase 2a; a capacity right is refused until OQ-12 closes; the future-start rules hold. A fully applied desired set with a future start reads `pending` with its effective time until that time passes, then `applied`. A Revoked posture whose revoke has a stuck step reads `pending`, and `applied` only after the step succeeds or the operator's confirm of it is accepted. While the first issue of a source runs, a changed desired set for it reads `refused` as retryable; after the first issue failed, `refused` as definitive. After BSS sends Revoked and then a new revision under the same source key, the new issue is accepted. A future-start set whose lineage is revoked, expires or is deleted before its effective time reads `refused` as preempted, naming the revoke, expiry or deletion, and never later reads `applied`. The same holds, naming the replace, when its scheduled version is replaced before it starts. A `CAP_BELOW_CONSUMED` injected after a removal was applied gives `pending`, marked partial, listing that removal; an applied addition whose undo the gear refuses is listed too. That result stays `pending` until a corrective revision arrives or BSS's reconcile closes it, and never reads `refused`, also after the operator settles the change. An apply whose validation cannot finish reads `refused` as retryable, and a resend of the same revision is processed again.
- [ ] Phase 1b, `cpt-cf-license-manager-fr-preparation-readiness`: a preparation pack is Effective from the request; it reports `ready` only when every Grant is effective, `failed` when its change ends failed, and `withdrawn` after cleanup.

## Phase 2a

- [ ] Phase 2a, `cpt-cf-license-manager-fr-seat-assign`: only an active user gets a seat; one assignment per Resource; at most one success for the last seat; a delegated Grant is never released. From Phase 2b, with an approved per-seat default, the seat and its user Quota succeed or fail as one outcome under one correlation id; an injected failure of the Quota step reports the assign as failed, with any partial state visible. Phase 1 seat binds made directly in license-enforcement are shown without being drift, and at Phase 2a each one is adopted once as a seat assignment with an audit entry; a binding that breaks an assignment rule is reported, not adopted.
- [ ] Phase 2a, `cpt-cf-license-manager-fr-seat-views`: counts match license-enforcement; an End User sees only their own assignments.
- [ ] Phase 2a, `cpt-cf-license-manager-fr-seat-bulk`: exclusions show with reasons, and the minimum guarantee holds when a step fails.
- [ ] Phase 2a, `cpt-cf-license-manager-fr-user-lifecycle-cascade` (G7): a suspended user's seats are unassigned and, from Phase 2b, the user's shares are reclaimed down to the protected minimum, within the cascade target; reactivation restores nothing. While the user is not active, a new seat or share for that user is rejected. A cascade step that the gears keep rejecting re-reads state, is retried and follows `cpt-cf-license-manager-fr-stuck-steps`; it never ends as failed.
- [ ] Phase 2a, `cpt-cf-license-manager-fr-low-seat-warning`: the warning appears at the threshold.
- [ ] Phase 2a, `cpt-cf-license-manager-fr-pack-renew`: renew changes only the end date of the Effective version; an Expired or terminated pack is not renewed.
- [ ] Phase 2a, `cpt-cf-license-manager-fr-pack-suspend-reinstate` (OQ-16): a suspended pack's capacity is not usable; reinstate restores the prior capacity, and usage and leases are kept once OQ-16 closes. From Phase 2c, reinstate applies a parent Quota raise deferred during the suspension.

## Phases 2a to 2c

- [ ] Phase 2, `cpt-cf-license-manager-nfr-change-latency`: each threshold in the requirement holds at its stated size.
- [ ] Phase 2, `cpt-cf-license-manager-nfr-aggregate-freshness`: every cached aggregate carries a timestamp and a freshness label, and one older than 5 minutes is labelled stale.

## Phase 2b

- [ ] Phase 2b, `cpt-cf-license-manager-fr-share-adjust-reclaim`: the total handed out never exceeds the Entitlement; a share below the user's protected minimum is rejected; a reclaim keeps the protected part. Every user licensing Quota carries the version's window, and revoke and expiry treat it as they treat the tenant Quota.
- [ ] Phase 2b, `cpt-cf-license-manager-fr-share-bulk`: a total above the Entitlement, or one share below a user's protected minimum, rejects the whole change and names the users; a bulk reclaim keeps each user's protected part.
- [ ] Phase 2b, `cpt-cf-license-manager-fr-contribution-model`: removing a seat contribution is never rejected and never cuts below consumption; the residual is shown and released when the counter allows.

## Phase 2c

- [ ] Phase 2c, `cpt-cf-license-manager-fr-child-delegation`: a delegate to a target that is not a direct child, to a self-managed direct child, to a child with a live lineage from another source, or to a child holding overlapping foreign state is rejected, each with its own reason; each delegated seat exists exactly once across parent and child; every child Entitlement records its parent provenance. Of a concurrent issue and delegate to one child, exactly one succeeds. Of two concurrent delegates from one parent Entitlement to different children, each within the free capacity but together above it, exactly one succeeds; never more than the free capacity is delegated. The same holds for a delegate racing a share change or a seat bind in the parent on the same Entitlement. After a failed first delegate, the child pack's version 1 reads "not applied"; a further delegate or a decrease for that child is rejected with a typed reason. The parent's end of the unapplied first delegate terminates the Child Delegation and the child pack lineage. It recalls the delegated seats and sub-grants, closes the child records and raises the parent Quota to its target amount. When the child has no bound seat and no sub-grant, it does not check the child's protected minimum.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-child-delegation`: two delegates from one parent Entitlement, each within the free capacity but together above it, are sent one after the other. The second arrives after the first is accepted and before it is applied. The first is accepted, and the second is rejected with a typed reason.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-child-delegation`: while a first delegate to a child is still running, the parent ends the unapplied first delegate. The running delegate ends as preempted and applies no further step. The Child Delegation and the child pack lineage are terminated, no sub-grant remains in the child, and the parent Quota is restored. Sent after the child's version 1 is applied, the same verb is rejected with a typed reason. A parent administrator with PDP scope in the parent but none in the child can send it, and cannot revoke an applied child lineage.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-child-delegation`: a first delegate fails after its sub-grants exist in the child, and a child user is bound to one. The parent's end of the unapplied first delegate is rejected with a typed reason and aggregate blocking counts only, and nothing changes.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-split-cap`: parent use plus all Child Delegations stay within the Entitlement at every instant, also when a step fails between the parent and child Quota writes; a decrease below the child's protected minimum is rejected with aggregate counts only. For a child recorded as `deleted`, a child-deletion step still outstanding 72 hours after its escalation no longer counts the delegated amount toward the total.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-child-disable`: Preserve changes nothing; Reclaim takes only the safe part; unreadable state allows only Preserve; deleting a child terminates its Child Delegation, recalls the delegated seats and raises the parent Quota after the child side confirms. A deleted child with bound seats and usage above its protected minimum ends terminated, with no protected-minimum check, and the parent Quota is raised once. When parent and child are deleted in one run, both cascades reach their end state, and the skipped parent raise is recorded. A child deletion that runs at the same time as a parent revoke reaches its end state, and the parent Quota is not raised after the parent revoke is recorded. An injected permanent denial of a deletion step is escalated as stuck. While a child-side deletion step is outstanding, the parent Quota is not raised and the delegated amount still counts as used by the parent. In a child recorded as `deleted`, a step still outstanding 72 hours after its escalation no longer holds the raise. The parent raise goes ahead with an operator signal, and the delegated amount no longer counts as used.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-child-disable`: suspend the parent pack, delete a child, then reinstate the parent. While the parent is suspended, the parent Quota raise is recorded as deferred. Reinstate applies it, so the parent's capacity is whole. With the parent pack terminated, the raise is skipped and recorded as skipped.
- [ ] Phase 2c, `cpt-cf-license-manager-fr-parent-cascade`: revoking the parent ends the child's access; a stale parent base is rejected. Renew, suspend and reinstate of the parent pack apply to each child pack. A parent replace issues a new Child Delegation version and a new child pack version for each child, or is rejected as a whole; a later decrease against those versions is accepted.

## Phase 2 (scheduled replacement)

- [ ] Phase 2, `cpt-cf-license-manager-fr-scheduled-replace` (OQ-15): both gears switch at the start with no License Manager action and no instant with one change but not the other; the start window, one staged replacement per lineage, revoke cancelling staging and the growth limit hold; a failed staging leaves nothing staged.
