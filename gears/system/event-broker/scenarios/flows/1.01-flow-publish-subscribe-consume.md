# Flow: publish → subscribe → consume → record position

The canonical end-to-end journey, shown as the **complete sequence of HTTP interactions** between clients and the broker. A producer publishes three events; a consumer establishes a group, JOINs, SEEKs, streams the events in order, closes the stream and SEEKs to record the last offset it processed; a new subscription in the same group then streams from one above that offset without a SEEK of its own.

Every request and response is shown inline. All three events hash to backend partition `0` of `gts.cf.core.events.topic.v1~acme.orders.v1` (4 backend partitions, `RF = 100`). Every partition below is a backend partition.

The opening `topology` frame reports the stored cursors from Exchange 6. Events then arrive on partition `0` in strict `sequence` order `100 -> 101 -> 102`; the other partitions are empty, so only heartbeats follow.

## Exchange 8 - Close the stream, then SEEK to offset 102

The consumer has processed offset `102` and closes the stream (it drops the connection). Closing releases the subscription's stream lease and leaves `{sub_id}` a disconnected member of the group until its `session_timeout` (`PT30S`) passes, so a SEEK is accepted again once the broker sees the connection close (typically when its next heartbeat write fails, every `heartbeat_interval_secs`, default 5); a SEEK while the stream is still open answers `409 StreamingInProgress`. SEEK is the only call that writes the group's stored cursor, and delivery does not move it. A SEEK to `102` stores `102`, and the next stream delivers from `103`.

```http
POST /v1/subscriptions/{sub_id}:seek HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json

{ "topology_version": 1, "positions": { "gts.cf.core.events.topic.v1~acme.orders.v1": [ { "partition": 0, "value": 102 } ] } }
```

```http
HTTP/1.1 200 OK
Content-Type: application/json

{ "positions": { "gts.cf.core.events.topic.v1~acme.orders.v1": [ { "partition": 0, "value": 102 } ] } }
```

## Exchange 9 - A new subscription resumes past offset 102

The consumer LEAVEs `{sub_id}` and JOINs a new subscription to the same group. The stored cursors are keyed by group and partition, not by subscription, so the new subscription opens its stream without a SEEK: the open reads the stored cursor of each assigned partition and delivers from one above it.

```http
DELETE /v1/subscriptions/{sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
```

```http
HTTP/1.1 204 No Content
```

The LEAVE leaves the group with no member, so the JOIN below starts the group's topology again at `topology_version` `1`.

## Side effects (cumulative)

- Backend partition `("acme.orders.v1", 0)` holds the three events at offsets `100`, `101`, `102`.
- Stored cursor for `({group_id}, "acme.orders.v1", 0)` advances `99 -> 102` across Exchanges 6 and 8.
- Stored cursor for `({group_id}, "acme.orders.v1", 1|2|3)` is initialized to `0` (empty partitions with RF = 1, seeded earliest -> cursor = RF - 1 = 0).
- `metric evbk_events_consumed_total incremented by 3` (not yet implemented, tracked in #5692).
