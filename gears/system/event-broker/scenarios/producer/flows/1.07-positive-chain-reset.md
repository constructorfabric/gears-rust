# Operator-driven chain reset

When a producer's chain state is unrecoverable (e.g., storage corruption, irrecoverable sequence gap), an operator resets the producer's chain on one topic while preserving the `producer_id`. The next publish to that topic starts a fresh chain from sequence 1.

## Setup

- Run [Register a chained producer](./1.01-positive-register-chained-producer.md). `{producer_id}` available.
- `evbk_producer_state({producer_id}, acme.orders.v1)` exists with `last_sequence = 42`.

## Request

```http
POST /v1/producers/{producer_id}:reset HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json

{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.v1"
}
```

## Expected response

- `200 OK`, no body.

## Side effects

- `evbk_producer_state({producer_id}, acme.orders.v1)` is deleted.
- One audit record is emitted on the `event_broker.events` target: `kind = "producer.chain_reset"` with `actor_subject_id`, `actor_subject_type`, `actor_tenant_id`, `producer_id`, `scope = "topic"` and `topic = gts.cf.core.events.topic.v1~acme.orders.v1`. A reset that fails (unknown or not-owned `producer_id`) emits none.
- Next publish to `acme.orders.v1` with `meta.previous = 0, meta.sequence = 1` is accepted.
- Omitting `topic` from the body resets **all** state rows for `{producer_id}`; the audit record then carries `scope = "all"` and `topic = "*"`.
