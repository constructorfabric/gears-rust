# Producer cursor recovery after desync

When a chained producer loses its local chain state (DB restore, crash, restart without persistent state), it reads the broker's last known sequence per topic and uses the returned values to re-seed its local counter before publishing again.

## Setup

- Run [Register a chained producer](./1.01-positive-register-chained-producer.md). `{producer_id}` available.
- The producer has published to `gts.cf.core.events.topic.v1~acme.orders.v1` (last sequence 7) and `gts.cf.core.events.topic.v1~acme.shipments.v1` (last sequence 3). The chain is kept per `(producer_id, topic)`; no partition is part of it.

## Request

```http
GET /v1/producers/{producer_id}/cursors HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
```

## Expected response

- `200 OK`

```json
{
  "producer_id": "{producer_id}",
  "client_agent": "order-service/1.0",
  "topics": [
    { "topic": "gts.cf.core.events.topic.v1~acme.orders.v1", "last_sequence": 7 },
    { "topic": "gts.cf.core.events.topic.v1~acme.shipments.v1", "last_sequence": 3 }
  ]
}
```

## Side effects

- No state changes. Read-only endpoint.
- The producer uses `last_sequence` values to set `meta.previous` in the next publish per topic:
  - Next publish to `acme.orders.v1`: `meta.previous = 7`, `meta.sequence = 8`.
  - Next publish to `acme.shipments.v1`: `meta.previous = 3`, `meta.sequence = 4`.

## Errors

- `403 Permission Denied` — caller's principal does not match `producer_id`'s registered owner.
- `404 Not Found` — producer not registered (or reaped).
