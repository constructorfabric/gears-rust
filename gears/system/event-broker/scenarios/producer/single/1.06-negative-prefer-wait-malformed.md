# Malformed `Prefer: wait` rejected

`Prefer: wait=N` (RFC 7240) opts into synchronous persistence, where `N` is a non-negative whole number of seconds. A value that is not one - a non-numeric token - is a malformed preference and is rejected `400 BadRequest`, not silently reinterpreted as async or as the cap. (A numeric value larger than the broker's ceiling is **not** malformed: it clamps to the cap - see [single/1.02](./1.02-positive-publish-sync-wait-persisted.md).)

Nothing is enqueued: the header is parsed before the event reaches the write path, so a rejected request writes no outbox row and moves no producer chain head.

## Setup

- Topic `acme.orders.v1` and event type `acme.orders.created.v1` registered.

## Request

```http
POST /v1/events HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json
Prefer: wait=soon

{
  "id": "a1b2c3d4-0000-0000-0000-0000000000a6",
  "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~",
  "tenant_id": "<tenant-uuid>",
  "source": "order-service",
  "subject": "order-906",
  "subject_type": "gts.cf.core.events.subject.v1~acme.order.v1",
  "occurred_at": "2026-05-29T10:06:00Z",
  "data": { "order_id": "order-906", "total_cents": 600 }
}
```

## Expected response

- `400 BadRequest`, an `invalid_argument` Problem whose `detail` states that `Prefer: wait` expects a non-negative whole number of seconds.

## Side effects

- None. No outbox row is enqueued and no producer chain head moves, so a later valid publish of the same chain link is newly accepted (`202`), not a duplicate (`200`).
