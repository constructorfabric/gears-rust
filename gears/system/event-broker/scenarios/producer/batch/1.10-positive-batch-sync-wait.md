# Batch publish synchronously (wait for backend persistence)

`Prefer: wait=N` (RFC 7240) applies to a `:batch` as a whole, with the status codes of a single publish: `201 Created` once every admitted event is stored, `202 Accepted` if the wait elapses first, `200 OK` when every event is a duplicate. The hold is on the admitted events only - a duplicate prefix is not waited on - so a batch mixing a duplicate and a new event is answered `201` once the new one is stored.

## Setup

- Topic `acme.orders.v1` and event type `acme.orders.created.v1` registered.

## Request

Two new events of one topic, published synchronously.

```http
POST /v1/events:batch HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json
Prefer: wait=5

{
  "events": [
    {
      "id": "e0000000-0000-0000-0000-000000001401",
      "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~",
      "tenant_id": "<tenant-uuid>",
      "source": "order-service",
      "subject": "order-sync-1",
      "subject_type": "gts.cf.core.events.subject.v1~acme.order.v1",
      "occurred_at": "2026-05-29T10:14:01Z",
      "data": { "order_id": "order-sync-1", "total_cents": 100 }
    },
    {
      "id": "e0000000-0000-0000-0000-000000001402",
      "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~",
      "tenant_id": "<tenant-uuid>",
      "source": "order-service",
      "subject": "order-sync-2",
      "subject_type": "gts.cf.core.events.subject.v1~acme.order.v1",
      "occurred_at": "2026-05-29T10:14:02Z",
      "data": { "order_id": "order-sync-2", "total_cents": 200 }
    }
  ]
}
```

## Expected response

- `201 Created`, no body - every admitted event is stored within the wait.
- `Preference-Applied: wait=5` (RFC 7240 §3): the applied wait, so a client can tell a synchronous answer from an ignored preference. A requested wait above the broker's ceiling reports the ceiling.

## Side effects

- The admitted events are enqueued as one traced outbox batch and stored on the backend before the `201` returns.
- A batch that admits nothing (every event a duplicate) is answered `200` at once and waits on nothing; a batch whose wait elapses before the backend stores every admitted event is answered `202`, the events staying enqueued.
