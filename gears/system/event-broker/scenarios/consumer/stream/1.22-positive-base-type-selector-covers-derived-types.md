# Base type selector delivers its derived types

An interest's `types` entries are matched against each event's `type` with GTS pattern semantics: a bare type id covers its derived types. An interest naming a base type is therefore delivered events of the base and of every type derived from it, and not events of a type of another family on the same topic.

## Setup

- Topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) has these event types:
  - the base `gts.cf.core.events.event.v1~acme.orders.x.created.v1~`;
  - two types derived from it (their schemas' `allOf` refers to the base), `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~` and `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.rush.v1~`;
  - a type of another family, `gts.cf.core.events.event.v1~acme.orders.x.shipped.v1~`.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) with one interest, then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`:

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
  "subject_tenant": "<tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~"]
}
```

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open, five events are published for `<tenant-uuid>`, in this order: A of type `...x.shipped.v1~`, B of the base, C of `...x.express.v1~`, D of `...x.rush.v1~`, then E of the base.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The `event` frames are B, C, D and E, in that order. Event A is never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-b-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-c-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-d-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.rush.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-e-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- The topic has one partition and A was stored first, so a stream that delivered A would deliver it before B.
- Event A stays stored; a subscription selecting its type receives it.
