# Derived type the consume scope leaves out is not delivered

A base type selector covers the types derived from it (a bare type id covers its derived types, matched with GTS pattern semantics), but the selector never widens what the caller may read. At JOIN the broker asks the policy for `consume` on the topic, naming the interest's patterns and the topic's registered types they match; the answer's scope may list the event types the caller may read. The consume scope then admits each type by its exact id: a derived type the scope does not list is skipped, even though the selector covers it. The JOIN is not refused, because the scope admits the base the selector names (see [JOIN for an exact event type the consume scope excludes](../../auth/1.10-negative-join-event-type-excluded-by-scope.md) for the refusal when it admits none).

## Setup

- The caller acts in its own tenant `<tenant-uuid>`, which is also the interest tenant.
- Topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) has the base `gts.cf.core.events.event.v1~acme.orders.x.created.v1~` and two types derived from it, `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~` and `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.rush.v1~`.
- The policy grants the caller `consume` on the topic in `<tenant-uuid>` for `gts.cf.core.events.event.v1~acme.orders.x.created.v1~` and `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.rush.v1~` only; `...express.v1~` is not listed.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) with one interest (`201`, `"unmatched_types": []`), then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`:

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
  "subject_tenant": "<tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~"]
}
```

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open, two events are published for `<tenant-uuid>`, in this order: A of `...express.v1~`, then B of the base.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The first `event` frame is B. Event A is never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-b-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "subject_tenant": "<tenant-uuid>", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- `subscription {sub_id} next frame is event <event-b-id>`: the topic has one partition and A was stored first.
- The stream's read position moves past A: a skipped event is examined, not waited on.
- Event A stays stored; a caller whose scope lists its type receives it.
