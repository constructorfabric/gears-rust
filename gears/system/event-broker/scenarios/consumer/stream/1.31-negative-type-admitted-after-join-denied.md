# Type admitted after the JOIN and denied is not delivered

A type admitted to `types-registry` after the JOIN is selected by the interest's patterns once the broker's specification refresh resolves it (matched with GTS pattern semantics: a bare type id covers its derived types). The open stream's answer does not cover the new type, so the first time an event of it reaches the stream the broker asks the policy for `consume` on the topic naming that one type; the consume scope then admits each type by its exact id. When the answer denies the type, its events are skipped and the stream goes on with the next event. The selector never widens what the caller may read. The allowed case is [Type admitted after the JOIN is delivered](1.30-positive-type-admitted-after-join.md).

## Setup

- The caller acts in its own tenant `<tenant-uuid>`, which is also the interest tenant.
- Topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) has the event type `gts.cf.core.events.event.v1~acme.orders.x.created.v1~`.
- The policy grants the caller `consume` on the topic in `<tenant-uuid>` for `gts.cf.core.events.event.v1~acme.orders.x.created.v1~`, and denies it for `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.audited.v1~`.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) with one interest (`201`, `"unmatched_types": []`), then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`:

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
  "subject_tenant": "<tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~"]
}
```

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open:

1. `...created.v1~acme.orders.x.audited.v1~`, derived from `...created.v1~` and on the same topic, is admitted through `POST /types-registry/v2/platform/entities`, and the broker lists it in `GET /v1/event-types` after its next refresh.
2. Two events are published for `<tenant-uuid>`, in this order: A of `...audited.v1~`, then B of `...created.v1~`.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The first `event` frame is B. Event A is never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-b-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "subject_tenant": "<tenant-uuid>", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- `subscription {sub_id} next frame is event <event-b-id>`: the topic has one partition and A was stored first.
- The stream's read position moves past A.
- Event A stays stored; a caller the policy allows its type receives it.
