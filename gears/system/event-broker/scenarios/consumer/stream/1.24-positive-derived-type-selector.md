# Derived type selector delivers neither its base nor a sibling

A bare type id covers its derived types, and only those: the interest's `types` entries are matched with GTS pattern semantics, so a derived type id does not cover the base it derives from, nor another type derived from the same base. An interest naming a derived type is delivered that type and the types derived from it.

## Setup

- Topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) has these event types:
  - the base `gts.cf.core.events.event.v1~acme.orders.x.created.v1~`;
  - two types derived from it, `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~` and its sibling `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.rush.v1~`;
  - `gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~acme.orders.x.priority.v1~`, derived from `...express.v1~`.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) with one interest, then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`:

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
  "subject_tenant": "<tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~"]
}
```

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open, five events are published for `<tenant-uuid>`, in this order: A of the base, B of `...rush.v1~`, C of `...express.v1~`, D of `...express.v1~acme.orders.x.priority.v1~`, then E of `...express.v1~`.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The `event` frames are C, D and E, in that order. Events A and B are never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-c-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-d-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~acme.orders.x.priority.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-e-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~acme.orders.x.express.v1~", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- The topic has one partition and A and B were stored first, so a stream that delivered them would deliver them before C.
- Events A and B stay stored; a subscription selecting their types receives them.
