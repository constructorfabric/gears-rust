# Selector without a minor version delivers its minor versions

An interest's `types` entries are matched with GTS pattern semantics: a version segment with no minor version (`v1`) covers every minor version of that major (`v1.0`, `v1.1`), and not another major (`v2`). The selector itself need not be registered: the JOIN reports an entry in `unmatched_types` only when no registered type of the topic matches it.

## Setup

- Topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) has these event types: `gts.cf.core.events.event.v1~acme.orders.x.created.v1.0~`, `gts.cf.core.events.event.v1~acme.orders.x.created.v1.1~` and `gts.cf.core.events.event.v1~acme.orders.x.created.v2~`. With the default configuration the registry refuses a minor version above 0 of any event type, so this setup needs the registry's compatibility waiver (tracked in #5987); with it, the registry admits `v1.1` only after `v1.0`, and refuses a major-only `v1~` beside them.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) with one interest, then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`. The JOIN `201` reports the interest with `"unmatched_types": []`.

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
  "subject_tenant": "<tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~"]
}
```

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open, four events are published for `<tenant-uuid>`, in this order: A of `...created.v1.0~`, B of `...created.v1.1~`, C of `...created.v2~`, then D of `...created.v1.0~`.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The `event` frames are A, B and D, in that order. Event C is never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-a-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1.0~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-b-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1.1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-d-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1.0~", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- The topic has one partition and C was stored before D, so a stream that delivered C would deliver it before D.
- Event C stays stored; a subscription selecting its type receives it.
