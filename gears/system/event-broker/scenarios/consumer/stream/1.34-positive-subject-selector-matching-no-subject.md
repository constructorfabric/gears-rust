# Subject-type selector matching no subject type delivers nothing

A JOIN whose `subject_types` names a subject type that no event type of the interest allows is not refused, and nothing reports it: `unmatched_types` lists only `types` entries, never `subject_types` entries. The selector is a delivery filter, matched with GTS pattern semantics against each event's `subject_type`, so the stream delivers that interest no event about another subject type.

## Setup

- Topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) has two event types: `gts.cf.core.events.event.v1~acme.orders.x.created.v1~`, which allows subject types `gts.acme.orders.x.customer.v1~` and `gts.acme.orders.x.supplier.v1~`, and `gts.cf.core.events.event.v1~acme.orders.x.marker.v1~`.
- Run [Create an anonymous group](../groups/1.01-positive-create-anonymous-group.md). Group id available as `{group_id}`.
- JOIN with two interests on the topic, for the same tenant: the first names `...x.created.v1~` with a subject-type selector `gts.acme.orders.x.auditor.v1~`, which that type does not allow; the second names only `...x.marker.v1~`, so a marker event shows how far the stream has read.

```http
POST /v1/subscriptions HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Content-Type: application/json

{
  "consumer_group": "{group_id}",
  "client_agent": "audit-worker/1.0.0",
  "interests": [
    {
      "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
      "subject_tenant": "<tenant-uuid>",
      "ownership_filter": "entire_tenant",
      "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~"],
      "subject_types": ["gts.acme.orders.x.auditor.v1~"]
    },
    {
      "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
      "subject_tenant": "<tenant-uuid>",
      "ownership_filter": "entire_tenant",
      "types": ["gts.cf.core.events.event.v1~acme.orders.x.marker.v1~"]
    }
  ]
}
```

- [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`.

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open, three events are published for `<tenant-uuid>`, in this order: A of `...x.created.v1~` with `subject_type` `gts.acme.orders.x.customer.v1~`, B of `...x.created.v1~` with `gts.acme.orders.x.supplier.v1~`, then C of `...x.marker.v1~`.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the topic and partition.
- The first `event` frame is the marker C. Events A and B are never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-c-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.marker.v1~", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- `subscription {sub_id} next frame is event <event-c-id>`: the topic has one partition and A and B were stored first.
- Events A and B stay stored; a subscription without the selector receives them.
