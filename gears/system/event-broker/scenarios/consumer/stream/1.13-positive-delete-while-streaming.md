# DELETE while streaming closes the connection immediately

`DELETE /v1/subscriptions/{id}` is the priority interrupt while a `:stream` is open. It is answered during the stream, as `GET /v1/subscriptions/{id}` is; a SEEK or a second stream is refused. It ends the stream at once: the open stream's last frame is a `control` frame with `code: "terminal"` and `reason: "lose_all"`, carrying the stream's current positions, and the broker then ends the response. The consumer initiated the teardown, so no re-JOIN is implied.

## Setup

- Run [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) → `{sub_id}`, SEEK every assigned partition.
- A [stream](1.01-positive-stream-multipart-frames.md) is open against `{sub_id}`.

## Request

```http
DELETE /v1/subscriptions/{sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
```

## Expected behavior

- `DELETE` returns `204 No Content`.
- The open `:stream` ends immediately: its last frame is a `control` frame with `code: "terminal"` and `reason: "lose_all"`, and the broker then ends the response.
- A subsequent `GET /v1/events:stream?subscription={sub_id}` returns `404 SubscriptionNotFound` (the subscription was removed - contrast `410` for a *terminated* id from a rebalance gain (not yet answered, tracked in #5977; what a gain-ended id answers today is in "Topology-Change Handling (Rebalance)" in [feature 0004](../../../docs/features/0004-consumption-transport.md))).

## Side effects

- The subscription is removed. It was the group's only member, so nothing rebalances; the consumer group itself stays, now with no active members (with other members, the group would rebalance).
- The group cursor survives; no re-JOIN is implied for the deleting consumer.
