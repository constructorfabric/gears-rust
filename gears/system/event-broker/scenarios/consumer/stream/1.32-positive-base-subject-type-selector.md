# Base subject-type selector delivers derived subject types

An interest's `subject_types` entries are matched against each event's `subject_type` like `types`, with GTS pattern semantics: a bare type id covers its derived types. A selector naming a base subject type is therefore delivered events about the base and about every subject type derived from it, and not events about another subject type. The exact form is [Subject-type selector](1.18-positive-subject-types-selector.md).

## Setup

- Event type `gts.cf.core.events.event.v1~acme.orders.x.created.v1~` on topic `gts.cf.core.events.topic.v1~acme.orders.x.orders.v1` (1 partition) allows subject types `gts.acme.orders.x.customer.v1~` (which covers its derived subject types, so `gts.acme.orders.x.customer.v1~acme.retail.x.member.v1~` may be published) and `gts.acme.orders.x.supplier.v1~`.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) with one interest that names the selector, then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{sub_id}`:

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.x.orders.v1",
  "subject_tenant": "<tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.x.created.v1~"],
  "subject_types": ["gts.acme.orders.x.customer.v1~"]
}
```

## Request

```http
GET /v1/events:stream?subscription={sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

Once the stream is open, four events of the type are published for `<tenant-uuid>`, in this order: A with `subject_type` `gts.acme.orders.x.customer.v1~acme.retail.x.member.v1~`, B with `gts.acme.orders.x.customer.v1~`, C with `gts.acme.orders.x.supplier.v1~`, then D with `gts.acme.orders.x.customer.v1~`.

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The `event` frames are A, B and D, in that order. Event C is never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-a-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "subject_type": "gts.acme.orders.x.customer.v1~acme.retail.x.member.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-b-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "subject_type": "gts.acme.orders.x.customer.v1~", "partition": 0, "sequence": <sequence>, ... } }
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-d-id>", "type": "gts.cf.core.events.event.v1~acme.orders.x.created.v1~", "subject_type": "gts.acme.orders.x.customer.v1~", "partition": 0, "sequence": <sequence>, ... } }
```

## Side effects

- The topic has one partition and C was stored before D, so a stream that delivered C would deliver it before D.
- Event C stays stored; a subscription without the selector receives it.
