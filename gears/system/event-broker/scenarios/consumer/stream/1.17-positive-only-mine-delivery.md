# Only-mine delivery skips unowned events and other owners' events

An interest with the default `ownership_filter`, `only_mine`, is delivered only events of the caller's tenant whose `subject_owner` is the caller. An event with no `subject_owner` (tenant-wide) and an event owned by another subject are not delivered to it. An `entire_tenant` interest on the same tenant is delivered all of them.

## Setup

- Event type `gts.cf.core.events.event.v1~acme.orders.created.v1~` on topic `gts.cf.core.events.topic.v1~acme.orders.topic.v1` (1 partition).
- The caller is subject `<caller-subject-uuid>` of tenant `<caller-tenant-uuid>`.
- [Cold JOIN](../subscriptions/1.01-positive-cold-join-fresh-group.md) of a fresh group with the interest below, then [SEEK earliest](../positions/1.01-positive-seek-earliest.md) → seeded `{only_mine_sub_id}`. The JOIN `201` echoes `"ownership_filter": "only_mine"` and `"subject_tenant": "<caller-tenant-uuid>"` ([JOIN only_mine](../subscriptions/1.14-positive-join-only-mine.md)).

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.topic.v1",
  "types": ["gts.cf.core.events.event.v1~acme.orders.created.v1~"]
}
```

- The same steps for a second fresh group with this interest → seeded `{entire_tenant_sub_id}`:

```json
{
  "topic": "gts.cf.core.events.topic.v1~acme.orders.topic.v1",
  "subject_tenant": "<caller-tenant-uuid>",
  "ownership_filter": "entire_tenant",
  "types": ["gts.cf.core.events.event.v1~acme.orders.created.v1~"]
}
```

- Three events of the type are published for `<caller-tenant-uuid>`, in this order: event A with no `subject_owner`, event B with `"subject_owner": "<other-subject-uuid>"`, then event C with `"subject_owner": "<caller-subject-uuid>"`.

## Request

```http
GET /v1/events:stream?subscription={only_mine_sub_id} HTTP/1.1
Host: broker.example.com
Authorization: Bearer <tenant-token>
Accept: multipart/mixed
```

## Expected response

- `200 OK`, `Content-Type: multipart/mixed; boundary=<...>`.
- The `topology` frame assigns the interest's topic and partition.
- The first `event` frame is event C, with its `subject_owner`. Events A and B are never delivered.

```
--<boundary>
Content-Type: application/json

{ "kind": "event", "payload": { "id": "<event-c-id>", "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~", "subject_tenant": "<caller-tenant-uuid>", "subject_owner": "<caller-subject-uuid>", "partition": 0, "sequence": <n>, ... } }
```

## Side effects

- `subscription {only_mine_sub_id} next frame is event <event-c-id>`: the topic has one partition and A and B were stored first, so a stream that ignored the ownership filter would deliver A first.
- `subscription {entire_tenant_sub_id}` delivers A, B and C, in that order. Event A's payload has no `subject_owner` key.
- Events A and B stay stored; only the delivery is filtered.
