# JOIN, stream or SEEK without `consume` on the consumer group → 403 ConsumerGroupNotAuthorized

Besides the creator check, JOIN asks the policy for `consume` on the consumer group itself: an anonymous group as the group family resource `gts.cf.core.events.consumer_group.v1~`, naming the group and its tenant, in that tenant; a named group as the group itself, in the caller's tenant (not yet implemented, tracked in #5702). A stream open and a SEEK, which writes the group's shared cursors, ask it again after the tenant check and the joiner check, and reuse an allow JOIN, a SEEK or an earlier open got for the same request for `streaming.authz_scope_ttl_secs`. A refusal is `403 Permission Denied` (`ConsumerGroupNotAuthorized`).

The shipped policies do not tell this apart from the tenant rule. tr-authz answers the group check with its rule for the group's tenant, which the group's creator in its own tenant always reaches, and static-authz allows it. Only an action-aware policy that grants `consume` on consumer groups separately refuses it.

## Setup

- Tenant `{tenant_id}`; topic `gts.cf.core.events.topic.v1~acme.orders.v1` with one partition and the event type `gts.cf.core.events.event.v1~acme.orders.created.v1~`.
- The policy grants principal A `define` on consumer groups and `consume` on the topic in `{tenant_id}`, but not `consume` on consumer groups.
- Principal A creates group `{group_id}` (`POST /v1/consumer-groups`).

## Request (principal A)

```http
POST /v1/subscriptions HTTP/1.1
Host: broker.example.com
Authorization: Bearer <principal-a-token>
Content-Type: application/json

{
  "consumer_group": "{group_id}",
  "client_agent": "worker/1.0.0",
  "interests": [
    {
      "topic": "gts.cf.core.events.topic.v1~acme.orders.v1",
      "subject_tenant": "{tenant_id}",
      "ownership_filter": "entire_tenant",
      "types": ["gts.cf.core.events.event.v1~acme.orders.created.v1~"]
    }
  ]
}
```

## Expected response

- `403 Permission Denied` (`ConsumerGroupNotAuthorized`)

```json
    "reason": "access denied by policy",

```

## Further exchanges: the grant revoked after JOIN

The policy grants `consume` on consumer groups; principal A JOINs `{group_id}` → `{sub_id}` and SEEKs partition 0 to `earliest`; then the grant is revoked. Once `streaming.authz_scope_ttl_secs` has passed since the last allow:

```
GET /v1/events:stream?subscription={sub_id}
Authorization: Bearer <principal-a-token>

→ 403 Permission Denied (ConsumerGroupNotAuthorized)
```

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "You do not have permission to perform this operation",
  "instance": "/v1/events:stream",
  "trace_id": "<request-trace-id>",
  "context": {
    "reason": "access denied by policy",
    "resource_type": "gts.cf.core.events.consumer_group.v1~"
  }
}
```

```
POST /v1/subscriptions/{sub_id}:seek
Authorization: Bearer <principal-a-token>
{ "topology_version": 1, "positions": { "gts.cf.core.events.topic.v1~acme.orders.v1": [{ "partition": 0, "value": "latest" }] } }

→ 403 Permission Denied (ConsumerGroupNotAuthorized)
```

The SEEK body is the stream's with `"instance": "/v1/subscriptions/{sub_id}:seek"`. The group check comes before the positions check, so a stream open of a subscription that was never seeked answers this `403`, not `409 PositionsNotSet`.

## Side effects

- The refused JOIN creates no subscription: principal A's `GET /v1/subscriptions` lists none for `{group_id}`.
- The refused stream open takes no lease: once the grant is restored, principal A's next `GET /v1/events:stream?subscription={sub_id}` opens.
- The refused SEEK writes no cursor: once the grant is restored, the stream of `{sub_id}` delivers partition 0 from `earliest`, the position of the allowed SEEK.
