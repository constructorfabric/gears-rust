# SEEK succeeds after a leave-triggered rebalance, once the client re-reads

When a member LEAVEs (or disconnects from) a consumer group, the group rebalances: a surviving member's assignment grows to take over the departed member's partitions and the group's `topology_version` is bumped. A SEEK the survivor issues with the version it observed before the departure is fenced off with `412 TopologyVersionMismatch` (the wholesale, atomic fence of [1.15](./1.15-negative-seek-stale-topology-version.md)). The survivor re-reads its subscription for the current `topology_version`, then re-seeks a partition it already held - which a leave never takes away - at that version, and succeeds. Same recovery flow as [1.16](./1.16-positive-seek-after-join-rebalance.md), with the topology bump caused by a LEAVE.

A partition the survivor newly *gained* from the departed member is reached by re-JOINing (a gain is terminal - the survivor commits, re-JOINs for a new `subscription_id`, and SEEKs the gained partition on the fresh subscription; see [flow docs](../flows/)). That is out of scope here: this scenario exercises the version fence and its re-seek recovery on the survivor's retained partitions.

## Setup

- Register `acme.orders.v1` with 4 partitions.
- Members A (`{sub_a}`) and B (`{sub_b}`) both JOIN the same group; the 4 partitions split 2/2. A owns `{S_a}` (2 partitions) at `topology_version` `2`.
- B leaves: `DELETE /v1/subscriptions/{sub_b}`. The rebalance bumps `topology_version` to `3` and reassigns all 4 partitions to A. A's original `{S_a}` is unchanged - a leave only adds partitions - and `("acme.orders.v1", {p_held})` is one A already held.

> **The growth is not observable on `{sub_a}`.** A gain terminates the survivor's subscription rather than updating its assignment in place, so `GET /v1/subscriptions/{sub_a}` keeps reporting A's pre-leave partitions, however long you wait. A learns of the change in-band, as a `control`/`terminal` frame on its open stream, and picks the freed partitions up only in the response to a fresh re-JOIN - see [stream/positive-1.12](../stream/1.12-positive-stream-terminates-on-rebalance-gain.md). The steps below are written against `{sub_a}` for the version fence alone; anything that needs the grown assignment belongs after that re-JOIN.

## Request 1 - SEEK at the stale pre-leave version

A echoes `topology_version` `2` (observed while B was present), for a partition it already held.

```http
POST /v1/subscriptions/{sub_a}:seek HTTP/1.1
Content-Type: application/json

{ "topology_version": 2,
  "positions": { "gts.cf.core.events.topic.v1~acme.orders.v1": [{ "partition": {p_held}, "value": "earliest" }] } }

→ 412 Precondition Failed  (topology_version_mismatch; minimal body - no topology_version, no assignment)
```

Nothing is applied - the fence rejects the whole request before any cursor write; the version A holds is stale.

## Recovery - re-read, then re-seek at the current version

```http
GET /v1/subscriptions/{sub_a} HTTP/1.1

→ 200  { ..., "topology_version": 3, "assigned": [ ..4 partitions.. ] }
```

```http
POST /v1/subscriptions/{sub_a}:seek HTTP/1.1
Content-Type: application/json

{ "topology_version": 3,
  "positions": { "gts.cf.core.events.topic.v1~acme.orders.v1": [{ "partition": {p_held}, "value": "earliest" }] } }

→ 200  { "positions": { "gts.cf.core.events.topic.v1~acme.orders.v1": [{ "partition": {p_held}, "value": 0 }] } }
```

## Side effects

- The first SEEK seeds no cursor (fenced).
- The re-seek at `topology_version` `3` seeds the group cursor for the retained partition `{p_held}`.
