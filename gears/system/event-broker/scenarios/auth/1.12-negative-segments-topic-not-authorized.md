# Segments for a topic the caller may not read → 403 before 404

A caller may read a topic's metadata when the policy lets it consume the topic, or else publish one of the topic's event types; both questions are asked in the caller's own tenant. `GET /v1/topics/segments` asks before it looks the topic up, so a caller the policy refuses gets `403 Permission Denied` (`TopicNotAuthorized`) whether or not the topic is registered: the answer does not tell a registered topic from a missing one. The topic id is parsed first, so a malformed one is still a `400`.

## Setup

- The deployment authenticates with static tokens. The token `<nil-tenant-token>` is bound to an identity with a fixed subject id and the nil tenant `00000000-0000-0000-0000-000000000000`.
- The policy grants that caller neither `consume` on any topic nor `produce` on any event type: the shipped policies refuse every request from a nil tenant.
- The topic `gts.cf.core.events.topic.v1~acme.orders.topic.v1` is registered; the topic `gts.cf.core.events.topic.v1~acme.unregistered.topic.v1` is not.

## Request

```http
GET /v1/topics/segments?topic=gts.cf.core.events.topic.v1~acme.orders.topic.v1&partition=0 HTTP/1.1
Host: broker.example.com
Authorization: Bearer <nil-tenant-token>
```

The same refusal answers `GET /v1/topics/segments?topic=gts.cf.core.events.topic.v1~acme.unregistered.topic.v1&partition=0`.

## Expected response

- `403 Permission Denied` (`TopicNotAuthorized`)

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "You do not have permission to perform this operation",
  "instance": "/v1/topics/segments",
  "trace_id": "<request-trace-id>",
  "context": {
    "reason": "access denied by policy",
    "resource_type": "gts.cf.core.events.topic.v1~"
  }
}
```

## Side effects

- None: the read changes nothing, and the unregistered topic does not answer `404 TopicNotFound`.
