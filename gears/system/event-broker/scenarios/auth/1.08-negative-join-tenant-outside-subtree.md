# JOIN for a tenant outside the caller's subtree → 403

An interest names the tenant whose events it reads in `subject_tenant`. For each group of interests (the same topic, tenant and barrier mode) the broker asks the policy once for `consume` on the topic, rooted at the interest's tenant only. A tenant outside the caller's subtree is not reachable, so the policy denies it. The broker then asks the tenant check alone, which is denied as well, so the JOIN is refused `403 TenantIdNotAuthorized`. A `consume` grant on the topic does not help: the policy decides the tenant reach in the same answer.

## Setup

- Tenant tree: `T123` (the caller's tenant) has the child `T234`; `T999` is not below `T123`.
- The caller, in `T123`, holds `consume` on `gts.cf.core.events.topic.v1~acme.orders.topic.v1` and `consume` on consumer groups.
- Group `{group_id}` exists, created by the caller.

## Request

```http
POST /v1/subscriptions HTTP/1.1
Host: broker.example.com
Authorization: Bearer <T123-token>
Content-Type: application/json

{
  "consumer_group": "{group_id}",
  "client_agent": "worker/1.0.0",
  "interests": [
    {
      "topic": "gts.cf.core.events.topic.v1~acme.orders.topic.v1",
      "subject_tenant": "<T999-uuid>",
      "ownership_filter": "entire_tenant",
      "types": ["gts.cf.core.events.event.v1~acme.orders.created.v1~"]
    }
  ]
}
```

## Expected response

- `403 Permission Denied` (`TenantIdNotAuthorized`)

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "You do not have permission to perform this operation",
  "instance": "/v1/subscriptions",
  "trace_id": "<request-trace-id>",
  "context": {
    "reason": "access denied by policy",
    "resource_type": "gts.cf.core.events.request.v1~"
  }
}
```

## Side effects

- No subscription is created; `GET /v1/subscriptions` for `{group_id}` lists none.
