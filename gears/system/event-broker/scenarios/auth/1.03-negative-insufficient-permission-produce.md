# Principal without a produce grant → 403

Publishing an event requires the `produce` action on the event's tenant (or, when that is denied, `produce_ignore_barrier` on the event type) and then `produce` on the event type; it also requires `produce` on the topic's GTS resource (the topic-level check is not yet implemented, tracked in #5719). A principal with a valid token but no `produce` grant is refused `403 TenantIdNotAuthorized` once the tenant check and the barrier right are both denied, before the broker looks up the event type or the topic, so the type check is never asked. Only the request's own checks run earlier, for example body parsing, its size, a nil tenant and the form of the type id.

## Request

```http
POST /v1/events HTTP/1.1
Host: broker.example.com
Authorization: Bearer <token-without-produce-grant>
Content-Type: application/json

{
  "id": "11111111-0000-0000-0000-000000000001",
  "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~",
  "subject_tenant": "<tenant-uuid>",
  "source": "order-service",
  "subject": "order-1",
  "subject_type": "gts.acme.shop.orders.order.v1~",
  "occurred_at": "2026-06-15T10:00:00Z",
  "data": { "order_id": "order-1" }
}
```

## Expected response

- `403 Permission Denied` (`TenantIdNotAuthorized`)

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "You do not have permission to perform this operation",
  "instance": "/v1/events",
  "trace_id": "<request-trace-id>",
  "context": {
    "reason": "<PDP deny reason, or \"access denied by policy\">",
    "resource_type": "gts.cf.core.events.request.v1~"
  }
}
```

## Side effects

- No event is stored or enqueued.
- The response does not reveal whether the topic exists, to prevent existence probing by unauthorized principals.
