# Publish across a barrier with the barrier right → 202

A self-managed tenant below the caller sits behind a barrier, so the tenant check (rooted at the event's tenant, barriers respected) denies it. The broker then asks for the barrier right: `produce_ignore_barrier` on the event type, rooted at the event's tenant with barriers ignored. A caller that holds it passes, and the type check (`produce` on the event type, rooted at the caller's own tenant) decides the rest.

## Setup

- Tenant tree: `T123` (the caller's tenant) has the child `T234`, which is self-managed (a barrier).
- The caller, in `T123`, holds `produce` and `produce_ignore_barrier` on `gts.cf.core.events.event.v1~acme.orders.created.v1~`.

## Request

```http
POST /v1/events HTTP/1.1
Host: broker.example.com
Authorization: Bearer <T123-token>
Content-Type: application/json

{
  "id": "11111111-0000-0000-0000-000000000107",
  "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~",
  "subject_tenant": "<T234-uuid>",
  "source": "order-service",
  "subject": "order-1",
  "subject_type": "gts.acme.shop.orders.order.v1~",
  "occurred_at": "2026-06-15T10:00:00Z",
  "data": { "order_id": "order-1" }
}
```

## Expected response

- `202 Accepted`, no body.

## Side effects

- The event is enqueued for `T234`.
- The policy is asked three times: the tenant check (denied), the barrier right (allowed), the type check (allowed).
- Without `produce_ignore_barrier` the same publish is refused `403 TenantIdNotAuthorized`, as in [auth/1.06](1.06-negative-tenant-outside-subtree.md).
