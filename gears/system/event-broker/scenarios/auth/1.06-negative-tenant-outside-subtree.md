# Publish to a tenant outside the caller's subtree → 403

A publish names the tenant its event belongs to in `subject_tenant`. The broker asks the policy whether the caller can reach that tenant, rooted at the event's tenant with barriers respected. A tenant outside the caller's subtree is not reachable, and the caller holds no barrier right that could reach it either, so the publish is refused `403 TenantIdNotAuthorized` before the broker looks up the event type or the topic. A grant for the event type does not help: the type check is only asked after the tenant check passes.

## Setup

- Tenant tree: `T123` (the caller's tenant) has the child `T234`; `T999` is not below `T123`.
- The caller, in `T123`, holds `produce` on `gts.cf.core.events.event.v1~acme.orders.created.v1~`.

## Request

```http
POST /v1/events HTTP/1.1
Host: broker.example.com
Authorization: Bearer <T123-token>
Content-Type: application/json

{
  "id": "11111111-0000-0000-0000-000000000106",
  "type": "gts.cf.core.events.event.v1~acme.orders.created.v1~",
  "subject_tenant": "<T999-uuid>",
  "source": "order-service",
  "subject": "order-1",
  "subject_type": "gts.acme.shop.orders.order.v1~",
  "occurred_at": "2026-06-15T10:00:00Z",
  "data": { "order_id": "order-1" }
}
```

## Expected response

- `403 Permission Denied` (`TenantIdNotAuthorized`)

```json
{
  "type": "gts://gts.cf.core.errors.err.v1~cf.core.err.permission_denied.v1~",
  "title": "Permission Denied",
  "status": 403,
  "detail": "You do not have permission to perform this operation",
  "instance": "/v1/events",
  "trace_id": "<request-trace-id>",
  "context": {
    "reason": "access denied by policy",
    "resource_type": "gts.cf.core.events.request.v1~"
  }
}
```

## Side effects

- No event is stored or enqueued.
- The response does not say which check refused the publish.
