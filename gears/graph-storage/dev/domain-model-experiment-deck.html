The domain model,
loaded as a graph

Studio's domain model → GTS types → Graph Storage, with no code written per type. What the experiment built, what it measured, and what it found.

Graph Storage gear · prototype v0.1.2·studio-internal / domain-model-ui tools·2026-09-07 → 09

TakeawayThree days, two repositories, one question: can the model itself be the API?

The idea

Edit the model's JSON, get a typed graph API

The architect's asks: generate properties and links for free, register them in GTS, load the graph, count objects and find explosion points, and filter or sort any field through the API.

TakeawayThe model is the configuration; the graph is the service. No code per type.

What we built

Three pieces, two repositories

tools/gts-export

Exporter

Reads the model manifest, resolves inheritance, maps every property type to JSON Schema, derives search and index traits, emits one registration batch. Self-validates ids and $refs. Optional --model-revision.

tools/graph-load

Loader

Generates instances from a per-entity volume profile, edges from the model's cardinalities, ingests in bounded batches, probes the API and writes a report with timings and explosion points.

gear v0.1.2

Graph Storage

Two additions: the chain ceiling became a setting, and the index trait now reaches $filter and $orderby with kinds resolved from the schema. 54 unit, 25 fake-store and 31 PostgreSQL conformance cases green.

Everything runs against the studio-web compose stand; the model's own npm test stays green.

TakeawayTwo small gear changes and two dependency-free scripts were enough to test the idea end to end.

TakeawayNothing of the model's meaning is lost in translation, and every payload is validated against it.

Metrics · the missing index

250 000 rows: what one expression index buys

range filter + order, $top=50, end to endAPIplanner
today: no index on the declared path104 – 218 msindex scan on type, filter over 250k rows, top-N sort · 100 ms
hand-made expression index matching the gear's statement10 – 14 msindex scan, 51 rows, no sort · 0.2 ms
same request without payload terms (API overhead)9 – 10 ms
 
CREATE INDEX ON node (tenant_id, gts_node_type_id, ((<expr>) IS NULL), <expr> DESC, node_key)
  WHERE deleted_at IS NULL;      -- built in 0.7 s, 34 MB for 250k rows

The gear's statement already has the shape the index serves; it cannot create the index, because the platform's secure ORM exposes no DDL to a gear. Filed as gears-rust #4721. Detail learned: the DDL must render the same expressions as the query, or the planner ignores the index for ordering.

TakeawayRange and order cost exactly one missing index; the platform, not the gear, has to allow it.

What the type system found

26 overrides the model cannot satisfy

21× version: integer on managed-object, string on 21 descendants Fix — two fields: a row revision and a semantic_version
3× status: children declare enums disjoint from the parent's Fix — parent declares the union and children narrow, or a separate field
2× scope: TextContent / string over the parent's enum Fix — a typo in the model; use the parent's enum

A derived GTS type must accept a subset of its base, and allOf branches evaluate independently, so an instance with version: "1.2.0" fails the parent and version: 3 fails the child: no instance satisfies both. The exporter keeps the ancestor's declaration and lists the conflicts; the same rule belongs in the model's own validator.

TakeawayTyping the model found 26 defects in the model itself; the rule belongs in its validator.

The model changes ten times

Model revisions in the type id

$ npm run gts:export -- --model-revision m8        # or: auto  (hash of the loaded entities)
  cf.studio.sdlc.requirement.v1~      →  cf.studio.sdlc_m8.requirement.v1~
  cf.studio.rel.implemented_by.v1~    →  cf.studio.rel_m8.implemented_by.v1~
  node keys                           →  m8:requirement:1
on the standresult
register revision m8 beside the unrevisioned set415 types, 560 ms; 190 + 190 node types by pattern; 13 925 objects loaded and queried
re-register an edited model (one more index path) under the same ids409 — already registered with a different schema
the same edit as revision m9200 — 415 types registered

The gear registers a type once and refuses a changed schema under a known id. A revision per upload makes every edit a fresh, complete set: no conflict, validation intact, no gear change. The price: old objects stay on the old revision until re-ingested, and the catalogue grows per revision. The product answer is an in-place update for compatible changes.

TakeawayEdit, upload, repeat: now without conflicts or database resets, at the price of revisions.

TakeawayStrengths are measured; each weakness has a known owner and a known next step.

Next

What would make it a product path

platform

DDL for declared paths

A typed index builder a gear may call at registration, so range and order run on an index. Filed with the 250k-row measurement as gears-rust #4721.

gear

Update a type in place

Accept compatible schema changes under the same id (new optional field, wider enum, new index path); require a migration for incompatible ones. Then "edit JSON, upload" keeps validation and filters.

model

Volumes and hygiene in the model

A volume class per entity and a fan-out bound per relation, a validator rule that overrides must narrow, and the 26 conflicts fixed by their owners.

Then the two pillars this experiment did not touch: parameterised widgets that read a type's declared fields and query them, and change events from the graph for a serverless runtime (emit_events exists as a trait, publication does not).

TakeawayA product path exists and is split by owner: platform, gear, model.
