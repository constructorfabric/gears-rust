**ID**: `cpt-cf-credstore-adr-immutable-value-versions`

## Context and Problem Statement

Shipped ([ADR-0001](0001-cpt-cf-credstore-adr-stateful-gear.md)–[0003](0003-cpt-cf-credstore-adr-value-fingerprint-fence.md)): the backend key `(tenant_id, reference, key-class)` is reused, so rotation overwrites in place; a write is a saga tracked by `status` (`provisioning`, `active`, `deprovisioning`, `declared`); `value_fp = HMAC(fence_key, value)` detects a row/backend mismatch and fails the read closed until a healing `If-Match: *` re-write; guarded and `If-Match: *` writes use opposite orderings; `deprovisioning` holds a name until the backend delete completes. Four hazards — a torn write reading as absence, a stuck `provisioning` row wedging a name, `deprovisioning` holding a name hostage, two write orderings — share one cause: row and backend can be observed mid-write, disagreeing about which bytes belong to a reference. Fence, saga, reaper and name retention manage that disagreement after the fact. Can it be made impossible, without a gc table, a maintenance job or any cleanup that correctness depends on? And, once it is, can the garbage a failure leaves behind be accounted for — every unreachable secret version covered by a durable obligation to remove it — instead of merely hoped to be removed by a later write?

## Decision Drivers

- **D1** — a row never points at bytes other than the ones it describes; unreachable, not detected and healed.
- **D2** — a failure between the stores costs garbage, never a wrong value, a closed read or a wedged name (for the tolerated faults).
- **D3** — one write ordering, whatever the precondition.
- **D4** — no name retention; no statuses beyond "has a value" and "has none".
- **D5** — the plugin is a versioned kv store: `put` returns the provider's version of the stored value; no list, no CAS, no transactions.
- **D6** — a read stays one SQL query plus one backend read.
- **D7** — no background work in the process: no workers or tasks, no timers, no database polling, no deferred or delayed tasks, no work at startup. Every store side effect is executed by the request that caused it; every `put` is announced in PG first (a write intent); a cleanup the request could not finish is a debt recorded in PG and executed by a later request that touches the same record. Several instances run at once (horizontal scaling), and PostgreSQL, the value store and the process may each lose the network or stop at any moment.
- **D8** — hygiene: an unreachable secret version is always covered by a durable obligation (a recorded cleanup debt or an open write intent), except the documented residuals. Safety (D1) never depends on it.

## Considered Options

- **O1** — in-place overwrite, saga and fence (shipped).
- **O2** — gear-minted `value_id` per write: every write lands under a fresh random key `(tenant_id, value_id)`, the row holds a pointer, a `credstore_value_gc` table with a `pending` intent tracks unreferenced versions, and a periodic maintenance job (`run_gc`) drains it (withdrawn).
- **O3** — backend-native versioning (Vault KV v2, GCP Secret Manager `SecretVersion`) used directly as the plugin contract.
- **O3'** — plugin-minted ordered versions under one key per record, with **inline best-effort cleanup** and no intents: the provider assigns a value version on `put` (ordered, where `destroy` is supported), the row holds it as a pointer, on a backend that supports `destroy` the writer destroys older versions inline after the commit (and its own version after a lost CAS, and the old version after a secret removal), and record deletion purges the key through the platform transactional outbox. This is what this ADR said before the review of aviator5 showed that rotated, removed and orphaned secrets can be retained forever when an inline call is skipped or the writer stops (four scenarios). Withdrawn.
- **O3'+** — O3' with **write intents and outbox-driven cleanup**: every `put` is announced in a PG table before it happens, every store side effect after a commit (destroy of older versions, of a lost version, of a removed version, purge of a key) is an outbox task enqueued in the very transaction that learned it is needed, and a reclaim of expired intents (at startup and piggybacked on writes) enqueues the purge of what a dead writer may have left. Withdrawn: delivery of outbox tasks and reclaim need background workers that poll the database (D7).
- **O3''** — O3' with **write intents and recorded cleanup debts, executed by the request, healed on access**: every `put` is announced in a PG table before it happens; every store side effect after a commit (destroy of older versions, of a lost version, of a removed version, purge of a key) is a debt row written in the very transaction that learned it is needed, and the request that wrote it executes it after a confirmed commit; what a request leaves undone is executed, or what a dead writer left is removed, by a later request that touches the same record or reference. No outbox, no reclaim process, no background work.
- **O4** — two-phase commit or an outbox coordinating row and backend as one distributed transaction for every write.

## Decision Outcome

**Chosen: O3''.** The row stays authoritative for metadata and holds `value_version`, the value version the provider returned from `put` (`NULL` = `declared`; not the row's own `version` counter). All versions of a record live under one store key `(tenant_id, record_id)`; a version is never overwritten. The principle: **every side effect on the value store is either announced in PostgreSQL before it happens (a write intent before each `put`) or recorded in PostgreSQL, in the same transaction that learned it is needed, as a cleanup debt and executed by the request that caused it; nothing runs in the background, and what a request leaves undone is healed by a later request that touches the same record.** A write announces itself, puts the bytes, then in one PG transaction retires its intent, switches the pointer, records the debt to destroy older versions (where the backend supports `destroy`) and removes expired intents of the record; after a confirmed commit the same request executes the debt. A secret removal switches the pointer to `NULL` and records the destroys in the same transaction. Deleting a record deletes the row and records a key purge in the same transaction. An intent whose writer is gone is removed by the next successful write to the record, or, for a create that never produced a row, by the next create or read of the same reference, which also records and executes the purge of its key. O1 detects instead of preventing and meets none of D1–D8. O2 needs a gc table, an intent row, a maintenance job and a fence key address just to find its own garbage. O3' cleans up by an inline best-effort call that a stopped or failing writer never repeats, so D8 fails. O3'+ makes the obligation durable but delivers it through background workers that poll the database, so D7 fails. O3'' keeps the position-based cleanup and the durable obligation and runs everything in the request; its price is one small intent table, one small debt table, one extra short PG transaction per secret write, and a few documented residuals that are removed only when a record is touched again. O4 fails on grounds unrelated to correctness (Pros and Cons).

### Data

`credstore_secrets` (authoritative for metadata) holds:

- `id` — the record identity, minted at create and never reused: a re-create mints a new `id`. It is also the record part of the store key.
- `version` — the row version for optimistic concurrency, +1 on every change, metadata or secret.
- `value_version` — the value version of the current secret in the store, as returned by `put` (TEXT, `NULL` means `declared`, no secret). It is distinct from `version`, the row's optimistic-concurrency counter (the **row version**, bumped on every change of the row and used in the `ETag` `(id, version)` and the CAS); the **value version** identifies the stored secret bytes.

The client validator is `(id, version)`. A new `id` on re-create means a validator from before a delete never matches: no ABA, no tombstones. The store holds, under `(tenant_id, record_id)`, immutable versions identified by the value versions the provider assigned.

`credstore_write_intents` (internal bookkeeping, not exposed and not tenant-scoped through the PDP) holds one row per secret write attempt between its announcement and its commit:

- `attempt_id` — primary key, minted per attempt (random, never reused);
- `tenant_id`, `record_id` — the store key the attempt will `put` under;
- `reference` (and the owner, where the reference is scoped to a private-class owner) — the record's reference, so that a create that never produced a row can be found by it;
- `lease_until` — database clock, `now() + lease`; before it the intent is protected, after it the intent may be healed by a later request (see Heal on access). The lease is the time allowed for healing, not a guard on the writer.

It is a before-the-fact log, not a task queue. It is read only by point lookups, by `(tenant_id, record_id)` and by `(tenant_id, reference)`; there is no scan by time. The lease is gear configuration, the block `write`: `intent_lease_secs` (default 300, at least 60). **Deployment requirement:** the lease must be markedly longer than the longest time a value store may still apply a request it has received (Vault cancels a request after its maximum request duration, 90 s by default); no in-process check enforces it.

`credstore_store_cleanup` (internal bookkeeping, the same schema migration) holds one row per cleanup debt, an obligation to remove something from the value store:

- `id` — primary key (UUID);
- `tenant_id`, `record_id` — the store key;
- `op` — `purge` (call `delete_key`) or `destroy` (call `destroy`);
- `selector` — `below` or `exact` for `destroy`, empty for `purge`;
- `version` — the value version for `destroy` (the same type as `value_version`), empty for `purge`;
- `created_at` — database clock.

It is read by point lookups on `(tenant_id, record_id)`. A debt row is written in the same PostgreSQL transaction that makes the store content dead, and it is executed by a request (see the protocol and Heal on access), never by a worker. Both kinds are idempotent and safe to execute at any later time, any number of times, by any instance: `destroy below vv` never touches `vv` or anything above it, `destroy exact` names a version no row will ever point at, and `purge` is recorded only for a record id that has no row and is never reused. A `destroy` debt is recorded only when the selected plugin supports `destroy`; a `purge` debt always. Deleting a debt row that is already deleted affects zero rows.

### The plugin contract

Three required operations and one optional. Every operation takes the record key explicitly, `key = (tenant_id, record_id)`, where `record_id` is the row's `id` (minted at create, never reused); the gear chooses the key and the plugin only maps it to a physical location under its installation prefix, so the reference, type and sharing are not part of the key. Every call also carries the request context, used only for correlation, never for authorization. Required: `put(key, value) -> version` (durable; the provider chooses the value version and `put` returns it, and the gear stores it in `value_version`), `get(key, version) -> Option<bytes>` (exactly the bytes written by the `put` that returned `version`, not found, or a permanent "unreadable" outcome meaning the version exists but can never be read, e.g. a lost decryption key — never different bytes) and `delete_key(key)` (delete the key with all its versions; idempotent). Optional: `destroy(key, selector)`, idempotent, where the selector is `Below(version)` (every version older than `version`) or `Exactly(version)` (that one version). The plugin declares whether it supports `destroy`. A backend that supports `destroy` **MUST** return **ordered versions per key** (a `put` that starts after another `put` on the same key has returned gets a greater version); a backend without `destroy` does not need ordered versions, because `Below(vv)` is safe only when every version older than a committed version belongs to a writer with a stale base. Every backend must also provide **durability** (`put` returns only after the bytes are durable) and **exact bytes**. Not required: CAS, listing, cross-key transactions, linearizability beyond the version ordering, server-side logic.

Backends with `destroy` and ordered versions: Vault and OpenBao KV v2 (the KV version number; the mount keeps 10 versions per key by default, which is enough because superseded versions are destroyed after each commit; the effective limit of a key is the larger of the mount's `max_versions` and the key's own, so an operator who wants more raises it on the mount, or on the key, and a per-key value can never lower the mount's; age-based expiry must stay disabled; if more versions than the limit accumulate above the pointer, Vault removes the oldest, possibly the one the row points at, and that record answers an internal error (500) until rewritten), Google Cloud Secret Manager (version numbers), a PostgreSQL plugin (a sequence-backed row id in an insert-only table), the in-memory plugin (a per-key counter) and a file plugin (a per-key monotonic counter, not a random id). Backends without `destroy`: AWS Secrets Manager (a version cannot be deleted; version ids are UUIDs, so unordered) and Azure Key Vault (a version can only be disabled; ids are opaque). They provide the three required operations only and accept the residual below: a rotated or removed secret stays in the backend until the record is deleted. The per-provider mapping is in DESIGN §4.3 and the requirement is `cpt-cf-credstore-fr-backend-compatibility`.

### The protocol

**Write** (`PUT` create or replace, `PATCH` carrying `secret`):

1. **Read and check.** Read the row (none for create). The same SQL also returns two existence flags, by point lookup and never a count: the record has pending debts, and the record has expired intents. Check the client precondition (`Matches` = `(id, version)`, or `Exists`), the PDP on the row's type (create: the request's type) before any store call, and the type traits. Create over an own row is 409, an expired one included (the expired record is visible: renew or delete it). A replace or `PATCH` finds an expired own row like a live one and updates it in place (renewal, same id). A create mints its record id here. If the database is unavailable for this read, the answer is 503 and nothing was written.
2. **Announce (tx0).** In its own transaction, insert the write intent `(attempt_id, tenant_id, record_id, reference, lease_until = now() + lease)`, with a fresh `attempt_id`. A definite failure is 503 and nothing was written to the store. An ambiguous tx0 is not verified: the answer is 503 and a harmless intent may remain, healed after the lease.
3. **Put.** `vv = put(key, value)` under the record's key; `vv` is the value version the provider assigned. A store error is 503; the intent stays and a later request heals it; an orphan version may exist (the failure can be ambiguous: the bytes can have persisted despite it).
4. **Commit (tx1), one PG transaction.** First delete the intent by `attempt_id`; it must affect exactly one row. Zero rows means the intent was healed (possible only for a writer alive past its lease, an out-of-model fault): roll the whole transaction back and answer 503; nothing else is done, and the version it put stays untracked (CORNER-CASES). Otherwise, in the same transaction:
   - *create*: insert the row `active` with `value_version = vv`. A unique violation (the reference is taken) is a definite loss: the intent deletion still commits together with a recorded `purge` debt for the key (the freshly minted record id can never get a row), and the answer is 409 `ALREADY_EXISTS`;
   - *replace / patch*: the CAS on the row version read in step 1. Success: record the debt `destroy below vv` (backend with `destroy`), and, when step 1 reported expired intents of this record, delete them (the condition `lease_until < now()` is checked again in the DELETE). Zero rows is a definite loss: in the same transaction record `destroy exact vv` if a row with this record id still exists, otherwise `purge` of the key; answer 409 `OPTIMISTIC_LOCK_FAILURE`. An `Exists` (last-writer-wins) update re-reads and retries once from step 1 with a **new** attempt before it returns 409;
   - tx1 fails definitely (the database is down, or the transaction retries are exhausted): 503; the version above the pointer and the intent remain and are healed by the record's next successful secret write or its delete, or, for a create, by the next create or read of the same reference;
   - tx1 fails ambiguously (the writer cannot tell whether the commit happened, for example the connection was lost around COMMIT): do not answer yet and execute nothing; run the **verification** below, once.

   Committed: execute the debts just recorded (step 5), then reply with the new validator (create 201 + `Location` + `ETag`; replace/patch 204 + `ETag`).

   **Verification** (after an ambiguous commit). A single verification transaction with a **locking read** (a plain read could race a commit that is merely delayed and applied later; the lock makes the verification wait for the ambiguous transaction to resolve). It locks the writer's own intent by `attempt_id` (tx1 deletes it first, so a pending tx1 holds that lock) and reads the record row:
   - the intent is still present: tx1 did not commit; run tx1 again in this transaction with the same version, the same base row version and the same rules, commit, and continue as after a normal commit;
   - the intent is gone and the row points at `vv`: tx1 committed; execute the record's pending debts and reply success;
   - the intent is gone and the row does not point at `vv`: the attempt did not take effect (the CAS was definitely lost); in this transaction record `destroy exact vv` (or `purge` when no row has the record id), only if no row points at `vv`, commit, execute it and answer 503;
   - the verification itself fails: 503 and nothing is executed.

   This is safe because a pointer at `vv` can only be set by this attempt's tx1 (versions are unique per key), because the locking read cannot observe a state that a still-pending ambiguous transaction will later change, and because `destroy exact vv` is recorded only in a transaction that sees no row pointing at `vv` and holds the lock a late tx1 would need. Every transaction of the protocol, the verification included, is retried by the platform's transaction retry for definite rollbacks (serialization failures, deadlocks); an ambiguous commit is never retried that way, and no store call runs inside a retried transaction.
5. **Execute the debts.** After a confirmed commit, the same request executes the debts it has just recorded (`destroy`, or `delete_key` for a purge) and deletes each debt row after success. A failure is logged and counted in `store_cleanup_failed_total`, the row stays, and the answer to the client does not change. After an ambiguous commit nothing is executed until the verification has resolved it. Debts of the record that step 1 found pending are executed the same way (see Heal on access).

There is no inline `destroy` outside this step, and no store call is made that was not recorded first. **No create over an expired own row**: an expired record still holds the reference, so a create-only write over it ends at step 1 with 409. Only a delete records a purge for a record that existed.

**Metadata-only patch** (no `secret` member): one PG CAS (`version + 1`); no store call and no intent.

**Remove the secret** (`PATCH {"secret": null}`, including suppression `{"fallback": "none", "secret": null}`, and a `PUT` with `null` over an `active` row): one PG transaction does the CAS that sets `value_version = NULL` (`declared`) and, where `destroy` is supported, records the debts `destroy below old_vv` and `destroy exact old_vv`, `old_vv` being the pointer that transaction nulled. No intent (nothing is put). After a confirmed commit the request executes the debts.

**Read**: one PG query resolves the hierarchy and picks the decisive row, and returns the existence flags; the PDP is evaluated on its type before any store call. A metadata-only read or a listing replies from PG and never touches the store. When the secret is selected: `get(key, value_version)`; found → reply; not found (a concurrent write switched the pointer and a destroy removed the old version) → re-read the row once and, if `value_version` changed, `get` again; a second miss after the pointer moved is 503. If the pointer did not move and the version is gone, or the plugin reports the version permanently unreadable, the read answers 500 Internal (canonical `Internal`, the diagnostic stripped from the wire) at once and logs an error, with no retry: with the tolerated faults this cannot happen, it means the store was damaged by an out-of-model fault, retrying cannot help, and the record must be rewritten (`PUT`/`PATCH` with a secret) or deleted. In a collection read with `secret` selected such an item fails the whole request, like any other backend read failure; an expired item is still returned without its secret. `value_version IS NULL` (`declared`) is never a store call. Expiry applies to the secret, not to the record: it is evaluated from the row at read time, and when the decisive row is `active` with `expires_at` in the past the read answers `SECRET_EXPIRED` (409) before any store call, never continuing to an ancestor's value; the record's metadata stays readable with status `expired`. A read that finds pending debts on the record executes them after answering its own question (best effort, see Heal on access); a read never removes an expired intent.

**Delete record**: read the row, check the precondition and the PDP (no row: 404). One PG transaction deletes the row (CAS on `version` for `Matches`) and records the `purge` debt for `(tenant_id, record_id)`. An ambiguous commit is resolved by a verification transaction that locks the record row: no row means the delete committed (execute the purge, 204), a present row means it did not (the delete is run again with the same precondition); if the verification fails, 503 and nothing is executed. The reference is free at once; a re-create mints a new id and a new key, which a lagging purge cannot touch. After a confirmed commit the request executes the purge. Reply 204.

**Executing a debt** is `delete_key` for `purge` and `destroy` with the row's selector and version for `destroy` (no call when the plugin does not support it), followed by deleting the debt row. Both are idempotent, so a repeat by another instance is harmless, and both may run at any time after their commit.

What each supported failure leaves behind and who removes it is catalogued per step in `CORNER-CASES.md` (added with the code in #4741) (the tolerated faults and their failure scenarios). The invariants that hold in every case:

- no pointer is committed without the writer's own intent being deleted in the same transaction, and tx1 requires exactly one deleted row;
- a debt is recorded in the transaction that makes the store content dead, and executed only after a confirmed commit;
- `destroy below vv` touches only versions strictly below a committed pointer; a secret removal uses `destroy`, never `delete_key`;
- nothing is executed after an ambiguous commit until a verification has resolved it, and a failed verification answers 503 with nothing executed;
- anything a request leaves undone is tracked in PG (an intent or a debt) and finished by a later request that touches the same record or reference.

A crash costs at most orphaned versions under one record key, and, outside the residuals below, each is covered by an open intent or a recorded debt until it is gone. Two guarded writers: the loser's CAS matches nothing → 409, and its tx1 records the removal of its own version. A secret removal whose CAS is lost is 409 and nothing was written; an ambiguous secret-removal commit is 503, and its debts, if it committed, are executed on the next access. Two `If-Match: *` writers: both announce and put; the first to commit owns the pointer, the other re-reads, retries once from step 1 with a new attempt and commits a later version, or returns 409.

### Why destroy is safe, and why `delete_key` is not used on the remove-secret path

`destroy(Below(vv))` deletes versions by position, so it is safe only because versions are ordered; this argument applies to `Below` only, and a backend without `destroy` needs neither it nor ordered versions. Let writer W commit `vv = r` and destroy below `r`. Another writer X can be in one of two situations. If X's `put` is **older** than `r` (X put, or read its base row, before W's commit), X holds a stale base: W's commit bumped `version`, so X's CAS matches nothing and X destroys its own version — the version W destroys was never going to be a pointer. If X's `put` is **newer** than `r`, X read the row after W's commit, which was after W's `put` returned, so by the ordering guarantee X's version is greater than `r` and `destroy(Below(r))` never touches it. Hence committed versions strictly increase in commit order, the row's current `value_version` is never destroyed, and a pointer never dangles. Without ordered versions neither half of the argument holds, which is why a backend without them cannot support `destroy`. `destroy(Exactly(vv))` needs no ordering: it names a version no row references.

The argument does not depend on **when** the destroy runs. A recorded `destroy below vv` may be executed right after the commit or much later, by another instance and after further writes: a version committed later was put after `vv`'s commit and is therefore greater than `vv`, so a `Below(vv)` that runs later still only touches versions that are older than a committed pointer and were never going to become one. The same holds for the pair `Below(old_vv)` and `Exactly(old_vv)` of a secret removal, which names only versions the removal itself made unreachable.

`delete_key` is never used on the remove-secret path. Removing the secret leaves the record alive as `declared`, and its key will be reused by the next write. A concurrent writer may already have put a newer version under that key and be about to commit, or may do so right after the removal commit; `delete_key` would delete that version before its pointer switch commits and leave a dangling pointer. The remove-secret path therefore deletes by position and by exact version (`destroy(Below(old_vv))`, `destroy(Exactly(old_vv))`), which can only touch versions the removal itself made unreachable. `delete_key` runs only after the row is gone, against a key no future record will use (record ids are never reused).

### Heal on access, and what the lease is for

There is no process that scans for leftovers. A request that touches a record or a reference finishes what an earlier request left undone:

- **Pending debts.** The single SQL that reads the record row also returns "this record has pending debts" and "this record has expired intents" (`EXISTS`, point lookups, `lease_until < now()` on the database clock). A read or a write of a record with pending debts executes them (best effort) and deletes the rows on success; a failure does not change the answer.
- **Expired intents of a live record.** They are deleted in tx1 of the next successful secret write to that record, the condition `lease_until < now()` being checked again in the DELETE. That write's `destroy below vv` also covers whatever version a crashed writer may have landed, because versions are ordered and the crashed writer's version is older. Reads do not touch expired intents: an orphan is never served.
- **A failed create.** The intent carries the record's `reference` (and owner where scoped). A create or a read of the same reference finds expired intents of that reference whose record id has **no row**, deletes them, and records and executes `purge` of their keys.
- **Idempotent and multi-instance.** Healing is idempotent and safe with several instances healing the same record at once: debts are safe to execute any number of times, and deleting an intent that is already gone affects zero rows.

Healing is a restricted reclaim: it acts only on a record or reference a request is touching, and only on intents past their lease. It deletes an intent and may record a `purge` of the key; it cannot dangle a pointer, whenever it runs and even against a writer that is still alive, for two reasons. First, tx1 can commit only while its intent exists: deleting it is the first thing tx1 does and it must affect exactly one row, so once a heal has taken the intent no pointer to the attempt's version can ever be committed; the writer rolls back and answers 503. Second, a purge is recorded only for a key whose record has no row, and record ids are never reused, so nobody will read that key again. **Safety therefore never depends on the lease.**

The lease decides *hygiene*: when a heal may act. An intent is protected until `lease_until`, and the lease is chosen well above the longest time a store may still apply a request (deployment requirement, see Data), so a live writer finishes its `put` before its intent can be healed. If that fails (a stall past the lease, or a store that applies a request late, both out-of-model), the writer's tx1 finds its intent gone, rolls back and answers 503, and its version stays untracked (residuals R2a, R2b).

### What remains

Residuals — R1 to R4b are garbage only and never affect consistency; R6 makes a record unreadable. The failure scenarios that leave them are catalogued in `CORNER-CASES.md` (added with the code in #4741):

1. **R1 — Orphan above the pointer of a live record** (a crash, a failed tx1 or a lost `put` answer after `put`): never served; its intent tracks it; removed by the record's next successful secret write or by the record's delete. A record never written or deleted again keeps it.
2. **R2a — Late put on a live record (untracked).** A `put` that the store applies after the writer's intent was healed lands above the new pointer with no intent and no debt. Never served; removed by the record's next successful write or delete.
3. **R2b — Late put on a dead key (untracked, permanent).** The same after the key was purged: nothing touches that key again. Closing R2a and R2b needs a conditional put in the plugin contract (see Revisit Triggers): not done.
4. **R3 — Backends without `destroy`** (AWS Secrets Manager, Azure Key Vault) keep rotated and removed versions, and orphans under a live key, until the record is deleted (there is no tenant offboarding: a deleted tenant's records stay, CORNER-CASES CC-913). Accepted.
5. **R4a — Tracked leftovers healed by access.** Debt rows of a live record whose execution failed or was interrupted, and the intents and orphan versions of a crashed write, stay tracked in the database until the record is read or written again (or, for a failed create, until its reference is created or read again); a record nobody touches again keeps them.
6. **R4b — Dead key.** A `purge` debt of a key that has no row — a deleted record, a lost create, a healed failed create, or a delete whose ambiguous commit was followed by a failed verification — whose execution failed or never ran (store down, process crash). No later access reaches it: the record has no row and its id is never reused. It stays until a possible external cleanup job.
7. **R6 — Version eviction.** More versions above the pointer than the store keeps (Vault and OpenBao `max_versions`, default 10; destroyed versions still count) make the store evict the pointed-at version, and that record answers an internal error (500) until rewritten. This happens after failed writes in a row and also from a burst of concurrent writers on one record, whose losing versions land after the winner's. An operator setting.

Not garbage, stated for completeness:

- **Integrity** comes from immutable versions and the exact-bytes `get`; a backend that returns different bytes violates its contract. Out-of-band tampering detection is not provided by the gear.
- **The PG database is the system of record for metadata** and must be backed up together with the store; the index is not rebuildable from the store (no listing). Index rebuild is out of scope.
- **Audit** events for secret reads and writes go through the platform event-broker gear and are best-effort: if publishing fails, the operation continues, an error is logged without the secret and the failure is counted in a metric.

### Statuses, and what is withdrawn

`CHECK (status IN (2, 4))` admits `active` and `declared` only; `provisioning`/`deprovisioning` are retired, their codes reserved. A row is either consistent — `value_version` names an existing version — or `declared` with no value version. `declared` is reached only on purpose: `PATCH {"secret": null}` on an existing record, or a creating `PUT` with an explicit `"secret": null` (no store call at all). `value_version IS NULL` holds exactly for `declared`.

Withdrawn by this ADR, relative to the shipped design and to O2: the `credstore_value_gc` table and its `pending` / `superseded` / `removed` / `aborted` reasons; the maintenance job, its entry point with its `gc` config and counters; the fingerprint fence — `value_fp`, `fp_key_id`, the stored fence key and its reserved address ([ADR-0003](0003-cpt-cf-credstore-adr-value-fingerprint-fence.md)): a row/backend mismatch is impossible by construction, so there is nothing for it to detect; the random per-write `value_id`; the **inline best-effort `destroy`** after a commit, after a lost CAS and after a secret removal, with the counters that described it (`destroy_failed`, `outbox_purge_failed`) and the key-purge queue, replaced by the intent journal, the cleanup-debt table and their counters. Kept: no name retention, two statuses, the generation-bound validator.

### The pattern

Nothing here is novel. Immutable versioned secrets with a pointer to the current one is how Vault KV v2, GCP Secret Manager, AWS Secrets Manager and Azure Key Vault work; credstore keeps the pointer in the metadata row so a versioned kv store qualifies (D5). The atomic pointer switch is copy-on-write / shadow paging (Lorie, 1977). Destroying below the committed pointer is garbage collection by position, which ordered versions make safe without a reachability scan. Recording a cleanup obligation in the very transaction that makes the store content dead is the transactional-outbox idea without a dispatcher: the obligation is durable, and the request executes it; the write intent is the matching pattern for a side effect that must be recorded before it happens (an intent log, as in write-ahead logging).

The reaper is removed, not reshaped. A saga has intermediate states that are wrong until repaired, and repairing them was the reaper's job. Immutable versions leave nothing to repair, and the leftover garbage is covered by a durable obligation, executed by the request that caused it or healed by a later request that touches the record, not by a timer or a worker.

### Consequences

- D1 is structural; a failure costs at most an orphaned version (D2); one ordering (D3); two statuses, no name retention (D4); a versioned kv plugin (three required operations plus an optional `destroy`) with no list and no CAS (D5); one query plus one backend read, with a rare bounded retry (D6); no background work: every store side effect is executed by the request that caused it, and leftovers are healed by a later request touching the same record (D7); every unreachable version is covered by a debt or an open intent, except the documented residuals (D8).
- Cost: one small intent table, one small debt table and one extra short PG transaction (tx0) per secret write; the hygiene guarantee rests on a deployment requirement (the lease is markedly longer than the longest time a store may still apply a request) that safety does not; a debt row per successful secret write on a backend with `destroy`; a failed execution is retried only when the record is touched again; a backend without `destroy` retains rotated and removed versions until record deletion; a backend with `destroy` must provide ordered versions; orphans above the pointer of a never-rewritten live record survive until its delete; the PG database is a system of record that needs a backup consistent with the store; an expired credential lingers (its metadata visible, its secret withheld) until it is renewed in place or deleted by its owner.
- Breaking for plugin authors only (`CredStorePluginClientV2`); no REST or SDK-consumer change — this ADR sits below [ADR-0004](0004-cpt-cf-credstore-adr-secret-value-exposure.md)'s surface. The reaper, its config and metrics are withdrawn; the cleanup counters are `store_cleanup_recorded_total` and `store_cleanup_failed_total` (per operation, `purge` or `destroy`; failed counts an immediate or heal-time execution that failed and left its debt row), `write_intents_healed_total` (expired intents removed by a heal), `write_commit_verified_total` (per operation, `write` or `delete`, and outcome: committed, not committed, not applied, failed), together with the read counters (`read_retry`) (DESIGN §10). There is no gauge of open intents or debts: counting rows is not allowed.
- **Data migration** is not the gear's work: the schema migration leaves every row `declared`, so the values are moved by a one-off, resumable operator tool that is not part of the gear and is removed once every installation has migrated. It runs during the downtime, between stopping the old version and starting the new one; it reads each value through the old store contract (so values an encrypting plugin keeps behind its own code are read in-process) and writes it through the new one, carrying it to the record's key with `put`. Before anything is written it verifies each value against its fingerprint, and the schema migration (which drops the fingerprint columns) is applied by the tool itself, only after the copy has succeeded; the tool then sets `value_version`, marks what it could not carry `fallback: none`, and tidies the orphan versions an interrupted copy left behind. Its progress is kept in its own tables in the gear's database, so after any failure the same command is run again and resumes. The schema migration refuses to run while credentials written before this release exist and the tool has not run, so a new version started too early fails at boot instead of discarding values. The old store's entries are retired by a separate, later `cleanup` command, once the migrated values are verified; the old fence key entry goes last and only on request (DESIGN §8). The tool runs stop-the-world with no concurrent writer, so it records no write intents.

### Confirmation

- **Model.** A bounded TLA+ model of the protocol, with reclaim disabled and cleanup debts executing at any time, repeatedly or never (immediately, at heal, or never), was checked exhaustively at small bounds: no dangling pointer, exact bytes, a committed value stays readable, versions ordered, reads linearizable, record ids never reused; and, with `destroy`, every unreachable version is covered by an open intent or a recorded debt. Mutations are caught: destroy below inclusive of the pointer, a debt executed before its commit, a loss without a debt, a purge with a live row, a CAS without the row version. Heal on access is a restricted reclaim, and safety under unrestricted reclaim at any time was already checked exhaustively; the heal steps themselves are not yet modelled.
- E2E: a replace commits and the process stops before any cleanup runs: the `destroy below` debt is in PG and the next read or write of the record executes it, after which the old version is gone; a secret removal likewise with its two debts.
- E2E: a replace killed after `put` leaves an orphan above the pointer and an open intent, the prior value keeps serving, and after the lease the record's next successful write deletes the intent and removes the orphan (R1); a create killed after `put` leaves an open intent, and after the lease the next create or read of the same reference deletes it and records and executes the purge of the key; a writer that put after a delete's purge ran finds its CAS lost and records the removal of its own version (`purge`, the row being gone).
- E2E: a CAS lost at the commit leaves the winner serving and, on a backend with `destroy`, records the removal of the loser's version in the same transaction; a create that loses to a concurrent create records a `purge`; two concurrent `If-Match: *` writers both complete or one returns 409, and the row points at a committed version (J1, J3); an ambiguous commit is verified under a lock: a commit that did happen answers success with its debts executed, one that did not is run again, an attempt that did not take effect records `destroy exact` only while no row points at the version and answers 503, and a failing verification answers 503 with nothing executed; a definite rollback (serialization failure, deadlock) is retried by the platform's transaction retry.
- E2E: an intent whose lease has not expired is never removed; no work runs at startup, and a failing execution of a debt leaves its row and does not change the answer.
- E2E: a read racing a pointer switch plus an executed destroy retries once and succeeds; a second miss after the pointer moved is 503, never a stale or empty value (J6). A row whose pointer did not move but whose version the store lacks, or which the plugin reports unreadable, answers 500 without a retry; in a collection read with `secret` selected such an item fails the request. `DELETE` immediately followed by `PUT` on the same reference succeeds without 409, the new record has a new id and key, and a lagging purge does not remove the new value (J7).
- E2E: on a backend without `destroy`, writes, reads and record deletion behave identically and no `destroy` debt is recorded or executed (`purge` debts still are); a failed execution is counted in `store_cleanup_failed_total` and retried when the record is touched again.
- Contract: versions under one key strictly increase in real-time `put` order (J4); the bytes at the row's `value_version` are the bytes of the write that committed it (J2); metadata-only reads, listings and metadata-only patches make no store call and write no intent (J5); `status` never holds a retired code and `value_version IS NULL` exactly for `declared`; the plugin sees `destroy` and `delete_key` only from the request that recorded or found the debt; no timer, no background task, no outbox and no maintenance entry point exist in the gear process.

## Revisit Triggers

- A target backend that must reclaim superseded versions cannot provide ordered versions (`destroy(Below)` requires them; such a backend needs its own ordered counter or must run without `destroy` and accept retention until record deletion).
- Orphan retention for never-rewritten records or never-retried failed debts hurts (R1, R4a, R4b): leftovers of a record nobody touches again survive. An external cleanup job that retries recorded debts and expired intents could be added then; it is deliberately not part of this decision.
- The late-put residuals (R2a, R2b) must be closed: a conditional put in the plugin contract would let a late `put` fail instead of landing after a heal or a purge. Vault and OpenBao KV v2 offer it (`cas`); GCP Secret Manager, AWS Secrets Manager and Azure Key Vault have no conditional version creation, so those backends would keep the residual.
- The PG database must become rebuildable from the store: that needs a listing capability on the plugin or a metadata copy in the store, neither of which is provided.
- Out-of-band tampering detection becomes a requirement: that needs a mechanism the fence's removal gave up (ADR-0003), and a story for key custody.

## Pros and Cons of the Options

- **O1 (shipped)** — Good: no migration, no SPI change, no backend garbage. Bad: a torn write serves 404 until a re-put (D1, D2); a stuck `provisioning` row wedges creation (D2, D4); `deprovisioning` holds a name hostage to a race its own key scheme creates (D4); two write orderings (D3).
- **O2 (withdrawn)** — Good: D1–D4 are met; plugin needs only `get`/`put`/`delete`. Bad: the gear mints ids the store cannot order, so it must record every intent in a `credstore_value_gc` table, run a maintenance job to drain it and reclaim stale `pending` rows, keep a fixed fence-key id, and still carries a narrow race between the job's backend delete and its gc delete; more moving parts (a table, a job, a config block, a trait, counters) than the problem needs.
- **O3' (inline best-effort cleanup, withdrawn)** — Good: no extra table, no intent row, no job; garbage is found by position; the backend is dumb (D5); one protocol for every precondition (D3); one PG transaction per write. Bad: the cleanup is a best-effort call after the commit, so a rotation whose destroy was skipped or whose writer stopped leaves the old version below the pointer, a secret removal whose destroy was lost leaves the removed secret in the store, a crashed create leaves a version under an id that never became a row, and a writer that put after a delete's purge leaves a version under a dead key; in every case nobody is responsible for the version and it can be retained forever (four scenarios). A backend with `destroy` must provide ordered versions, and one without it retains superseded versions until record deletion.
- **O3'+ (outbox and reclaim, withdrawn)** — Good: every unreachable version is covered by a durable obligation, an outbox task or an open intent; garbage is found by position. Bad: delivery of outbox tasks and the reclaim of expired intents need background workers that poll the database, which D7 does not allow.
- **O3'' (recorded debts, executed by the request, healed on access; chosen)** — Good: every unreachable version is covered by a durable obligation, a debt row or an open intent, except the documented residuals (D8); garbage is still found by position, with no listing and no gc table; the backend stays dumb (D5); one protocol for every precondition (D3); nothing runs in the background (D7); safety does not depend on the lease or on any cleanup. Bad: one small intent table, one small debt table and one extra short PG transaction per secret write; the hygiene guarantee rests on a lease deployment requirement, and the late-put residuals can be closed only with a conditional put in the plugin contract; a failed cleanup and an orphan wait until the record or reference is touched again; a backend with `destroy` must provide ordered versions, and one without it retains superseded versions until record deletion; orphans above the pointer of a never-rewritten live record linger until its delete; the PG database becomes a system of record that must be backed up with the store. Rejected variants: delayed destruction (a `not_before` on the cleanup) needs a timer or a deferred task and lengthens the retention of old secrets, while reads already tolerate a destroy through one re-read; recovery of plugin-minted versions through the plugin contract is not needed, because dead keys are purged whole (`delete_key`) and live-key orphans are the documented residual.
- **O3** — Good: a backend with native history needs no gear-side versioning. The earlier critique — that native versioning excludes every backend without it, including the in-memory plugin — was wrong: an in-memory plugin mints versions with a counter, and so can a file or PostgreSQL plugin. What matters is not native versioning but the version returned by `put` (ordered, where `destroy` is supported). O3'' is O3 stated as a contract on the plugin (versions from `put`) instead of as a property of particular products.
- **O4** — Good: the textbook answer for a write across two stores. Bad: a coordinator or outbox dispatcher on every write is a component and a failure mode of its own, and remote I/O inside a coordinated critical section is what the platform's cluster primitives avoid. O3'' records a durable cleanup obligation only for side effects that must follow a commit and are naturally idempotent (the key purge and the destroys), executes it in the request, and uses the intent journal only for the one effect that precedes the commit (the `put`).
