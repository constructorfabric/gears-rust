# CredStore: out of scope

What this version of CredStore does not handle. The service handles, with no background work, a process crash at any step, PostgreSQL unavailable or a lost commit, transaction contention, Vault errors and timeouts, concurrent writes and deletes, and an unavailable audit broker (DESIGN §6.2). The cases below fall outside that; each says what happens and what it costs. They are accepted risks of this version, covered by the runbook and monitoring.

- **CC-1.** Vault applies a write late (the client gave up after the plugin timeout, or the timeout is set close to the lease), after another write healed the expired write intent and moved the pointer. The client got 503. The late version lands above the pointer with no intent and no cleanup debt; it is never served, and the record's next successful secret write or its delete removes it.

- **CC-2.** Vault applies a write late, after the record's key was already removed (a deleted record or a healed failed create). The key exists again with that version, and nothing in the DB points to it. Record ids are never reused, so the key stays forever.

- **CC-3.** Vault evicts the version under the record's pointer. `max_versions` is 10 by default and destroyed versions count, so ten or more versions written above the pointer evict it. They come from failed writes in a row, or from a burst of concurrent writers on one record with no failure at all: the winner commits first and the losers' versions land above it. Reads answer 500 until the record is overwritten or deleted. A larger `max_versions` raises the threshold; a single writer per record or a conditional `put` would prevent it, and neither is in this version.

- **CC-4.** The version under the pointer is missing in Vault: an administrator deleted or destroyed it, `delete_version_after` expired it, a non-durable store (the in-memory plugin) lost it on a restart, or the DB was restored from a backup newer than Vault. A read answers 500 and logs an error until the record is overwritten or deleted; the service does not detect the divergence. A non-durable store also reuses version numbers after a restart, so another value can be served under an old pointer without notice; such a store is forbidden in production.

- **CC-5.** The DB was restored from a backup older than Vault. Pointers may reference versions already destroyed, and their reads answer 500 until the record is overwritten or deleted. Records created after the backup have no row, so their keys stay in Vault untracked forever. The outcome is undefined.

- **CC-6.** The operator misconfigures the Vault mount; the service neither reads nor checks its options. A `max_versions` below 10 brings the eviction of CC-3 closer; `delete_version_after` expires versions under pointers, and reads answer 500 as in CC-4; with `cas_required` every `put` is rejected and no secret can be written. It lasts until the operator fixes the mount.

- **CC-7.** Someone with direct access to Vault storage replaces the bytes of a version or writes a new one. The service does not detect it: a tampered version under the pointer is served as an ordinary value. A version written above the pointer is never served, and the record's next secret write or delete removes it; the tampering itself stays unnoticed.

- **CC-8.** Someone changes the gear's PostgreSQL tables bypassing the service (manual SQL, a hand-written migration). A deleted record row makes the record disappear (404), and its key stays in Vault forever. An edited pointer makes a read serve another existing version without notice, or answer 500. Deleted write intents or cleanup debts leave the versions they tracked untracked: the next secret write or delete of a live record removes them, nothing removes them for a key without a row. The service detects none of this.

- **CC-9.** The process or VM freezes for longer than the write-intent lease (300 s by default) at any step; nothing in the process checks the elapsed time. A write whose intent another write healed meanwhile rolls back on waking and answers 503; its version stays above the pointer untracked as in CC-1, and for a create the key it re-creates stays forever as in CC-2. A frozen create widens the race of CC-10, a frozen audit publish times out and loses the event, and requests to the same record wait on the frozen transaction's row locks. No pointer to a missing version is ever committed.

- **CC-10.** Two creates of one reference with different types, one in a tenant and one in its descendant, run at the same time (private records are not checked). Each type check runs before the other's row exists, which appears only after the value is stored, normally milliseconds later. Both succeed and the records carry different types, so a consumer reading by reference gets a secret of another shape depending on the tenant it reads in. Nobody gets an error and nothing is left; the mismatch stays until one record is deleted and re-created.

- **CC-11.** A tenant with its own non-private record of a reference with type A is moved under a parent that shares a record of the same reference with type B (Account Management does not offer moving yet). No create runs, so no type check runs, and descendants get type A or B depending on the branch; inheritance follows the new hierarchy at once. Nobody gets an error; the mismatch stays until one record is deleted and re-created.

- **CC-12.** Account Management deletes a tenant that still holds records; it sends no events and the service has no offboarding. The rows, write intents and cleanup debts stay in the DB, and the keys with all their versions stay in Vault. No request can reach them, so they stay until an operator or a future external job removes them.

- **CC-13.** A tenant that holds a `shared` record is suspended or soft-deleted while its descendants stay active. The service never looks at tenant status, so the descendants keep resolving the reference to that record. Whether a suspended ancestor's credentials should stop being inherited is not decided; today they are served until the record is deleted or the tenant leaves the chain.

- **CC-14.** A write crashed or lost its answer and the client never retries. Reads of an existing record run its cleanup debts but do not heal write intents, so the unserved version and the expired intent stay, tracked in the DB, while nobody writes a secret to or deletes the record (for a failed create: while nobody creates or reads the reference). Cleanup debts that failed to run likewise stay until the record is read or written again. If the record or reference is never touched, they stay forever.

- **CC-15.** The cleanup debt that deletes the key of a record with no row (a deleted record, a lost create, a healed failed create) does not run: Vault is down, the process crashes, or a delete's lost commit cannot be verified because PostgreSQL is down (the client gets 503, and a repeated delete answers 404). No request ever comes back to a record without a row, so the debt and the key stay, tracked in the DB, until an external cleanup job, which this version does not have.

- **CC-16.** Instances of the old and new service versions run at the same time on the same DB and Vault. They use different protocols and do not see each other's state; a mixed rollout is not supported, and the migration expects the old version to be stopped. The outcome is undefined: untracked write intents, cleanup debts and versions are possible in the DB and Vault.

- **CC-17.** Write intents and cleanup debts pile up in the DB and the operator cannot see how many: counting rows is forbidden, and the metrics count events, not what is outstanding (the intent of a crashed writer raises no metric at all).
